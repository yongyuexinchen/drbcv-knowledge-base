# 异常响应处理

## 类型判定
procedure — 三步流程：导入 HTTPException → 写判断条件 → raise 抛出异常（必填 status_code + 可选的 detail 信息）。

## 类比 ★
### 一句话比喻
异常响应处理就像餐厅统一的**"对不起，这道菜做不了"**话术——客人点了一份菜单上没有的菜（ID 超出范围），服务员不会把后厨的混乱场面（Python traceback）端给客人看，而是微笑着说一句"您查找的新闻不存在"（`detail`），并在小票上标注 404（`status_code`）。优雅、统一、不让客人看到后厨炸锅。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| `HTTPException` | 统一道歉话术模板——每个服务员都用同样的措辞 |
| `status_code=404` | 小票上的错误编号——404 = "没这道菜"，400 = "你点的有问题" |
| `detail="新闻不存在"` | 口头告知的具体原因——让客人知道为什么没上菜 |
| `raise HTTPException(...)` | 服务员中断正常流程——这道菜做不了，后面的菜也不做了 |
| `if id not in id_list` | 后厨检查库存——发现缺食材才触发道歉 |

## 是什么
`HTTPException` 是 FastAPI 提供的**异常响应机制**，用于在接口处理过程中主动中断正常流程并返回标准化的错误信息。通过 `raise HTTPException(status_code=..., detail=...)`，可以向客户端返回带有 HTTP 状态码和错误描述的 JSON 响应，替代 Python 原生的丑陋 traceback。

## 输入-输出空间
- **输入**：业务逻辑中的异常判断条件（如 ID 不存在、权限不足、参数无效）
- **输出**：JSON 格式的错误响应（包含 status_code 和 detail）
- **前置条件**：`from fastapi import HTTPException`

## 核心代码
```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

# 按 ID 查新闻，ID 只存在于 1-6
id_list = [1, 2, 3, 4, 5, 6]

@app.get("/news/{id}")
async def get_news(id: int):
    # 判断条件：ID 不在合法范围内
    if id not in id_list:
        # 抛出异常：中断正常流程，返回错误响应
        raise HTTPException(
            status_code=404,                    # 必填：HTTP 状态码
            detail="您查找的新闻不存在"          # 可选但推荐：错误描述
        )
    # 正常流程
    return {"id": id, "title": f"新闻标题{id}"}

# 访问 /news/2  → 200 OK，正常返回新闻
# 访问 /news/20 → 404，{"detail": "您查找的新闻不存在"}
```

| 步骤 | 代码 | 说明 |
|------|------|------|
| ① 导入 | `from fastapi import HTTPException` | 导入异常类 |
| ② 写判断条件 | `if id not in id_list:` | 业务逻辑：什么时候算"异常" |
| ③ raise 抛出 | `raise HTTPException(status_code=404, detail=...)` | `raise`（不是 return）中断流程 |
| ④ 必填 status_code | `status_code=404` | HTTP 状态码：400 客户端错误 / 500 服务端错误 |
| ⑤ 可选 detail | `detail="新闻不存在"` | 返回给客户端的 JSON，建议必写 |

## 正例（≥2 个）
1. **资源未找到**：用户请求 `/news/99` 但只有 6 条新闻 → `raise HTTPException(status_code=404, detail="您查找的新闻不存在")`。
2. **权限不足**：普通用户试图删除管理员文章 → `raise HTTPException(status_code=403, detail="无权限执行此操作")`。
3. **参数校验失败**：注册时用户名已存在 → `raise HTTPException(status_code=400, detail="用户名已被占用")`。

## 反例/边界（≥1 个）
1. **用 return 代替 raise**：`return HTTPException(...)` → 不会抛出异常，只是返回了异常对象本身，客户端收到的是一个奇怪的 Python 对象序列化结果，而不是标准错误响应。
2. **忘记写 detail**：只写 `raise HTTPException(status_code=404)` → 客户端收到 `{"detail": "Not Found"}`（默认值），用户体验差，不知道具体什么没找到。
3. **状态码用错**：资源未找到应该用 404，如果误写成 500 → 运维看到 500 以为服务器崩了，实际只是数据不存在，误导排查方向。

## 详细解释
常用 HTTP 状态码速查：
| 状态码 | 含义 | 场景 |
|--------|------|------|
| 400 | Bad Request | 请求参数错误、格式不对 |
| 401 | Unauthorized | 未登录/Token 无效 |
| 403 | Forbidden | 已登录但无权限 |
| 404 | Not Found | 资源不存在 |
| 422 | Unprocessable Entity | Pydantic 校验失败（FastAPI 自动抛出） |
| 500 | Internal Server Error | 服务器内部错误 |

**HTTPException vs Pydantic 校验错误**：
- Pydantic 的 422 错误是 FastAPI **自动抛出**的（参数类型不匹配、范围越界等），程序员无需手动处理。
- `HTTPException` 是程序员**主动 raise** 的（业务逻辑异常），用于处理 Pydantic 覆盖不了的场景（如数据不存在、权限验证失败）。
