# 用户模块总结

## 类型判定
discriminant — 定义用户模块的完整链路和与其他模块的边界差异，提炼通用开发模式。

## 类比 ★
### 一句话比喻
用户模块就像一个完整的会员体系——从办卡（注册）、刷卡进门（登录）、出示会员卡证明身份（Token）、查看会员信息（获取信息）、到去前台更新资料（修改信息）或挂失重设密码（修改密码），整个链条环环相扣。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| 注册 → 自动发 Token | 办会员卡 → 当场拿到卡，不用二次激活 |
| 登录 → 刷新 Token | 刷卡进店 → 确认会员身份，卡的有效期延长 |
| Token 7 天过期 | 会员卡年费到期——过期了得续费（重新登录） |
| 获取个人信息 | 出示会员卡查积分和消费记录 |
| 修改信息（可选字段） | 去前台改手机号——只改你说了的，其他不动 |
| 修改密码（先验旧密码） | 改支付密码——先输一遍旧密码确认是本人 |
| 全局异常处理器 | 会员中心统一客服话术——不管哪个窗口出问题，回复格式都一样 |

## 是什么
用户模块是头条项目的基础认证模块，包含注册、登录、Token 认证、获取个人信息、修改信息、修改密码六大核心接口。用户模块的核心价值是为后续收藏、浏览历史等模块提供统一的认证基础设施（Token 验证依赖注入、通用响应格式、全局异常处理）。

## 完整链路
```
注册 ──→ 登录 ──→ Token 验证 ──→ 获取个人信息
  │                              │
  │                              ├──→ 修改个人信息
  │                              │
  │                              └──→ 修改密码
  │
  └──→ 注册即登录（自动返回 Token）
```

## 通用开发模式（接口开发四步流程）
用户模块和新闻模块在开发流程上完全一致，验证了"接口开发四步流程"的通用性：

| 步骤 | 说明 | 用户模块示例 |
|------|------|------------|
| ① 模块化路由 | APIRouter + prefix + tags | `APIRouter(prefix="/api/user", tags=["users"])` |
| ② ORM 模型类 | 映射数据库表 | `User(Base)`, `UserToken(Base)` |
| ③ CRUD 封装 | 封装增删改查方法 | `authenticate_user()`, `update_user()`, `change_password()` |
| ④ 路由调用响应 | Depends 注入 → await CRUD → return | `Depends(get_current_user)` → `success_response()` |

## 用户模块独有的新知识
| 知识点 | 所在卡片 | 一句话 |
|--------|---------|--------|
| bcrypt 密码加密 | [[用户注册]] | 用 passlib 的 CryptContext 做哈希，不存明文 |
| UUID Token 生成 | [[Token生成]] | UUID4 随机生成 + 7 天过期时间 |
| 通用成功响应格式 | [[通用成功响应格式]] | `success_response()` + model_validate 从 ORM 脱敏取值 |
| 全局异常处理器 | [[全局异常处理器]] | 四类异常：业务层 → 数据完整性 → 数据库层 → 兜底 |
| Header 提取 Token | [[获取用户信息]] | `Header(..., alias="Authorization")` 从请求头取 |
| 依赖注入认证用户 | [[获取用户信息]] | `Depends(get_current_user)` 一次定义，多处复用 |
| model_dump 排除未设字段 | [[修改用户信息与密码]] | `exclude_unset=True, exclude_none=True` 只改传了的 |
| db.add 确保提交 | [[修改用户信息与密码]] | 改密码时 `db.add(user)` 确保 session 过期也能提交 |

## 正例（≥2 个）
1. **完整用户体验链路**：用户注册"大秋" → 自动返回 Token → 前端跳转"我的"页面 → 调用 info 接口获取个人信息 → 用户修改简介 → 调用 update 接口更新 → 前端重新渲染新简介。
2. **Token 过期处理**：用户 8 天未使用 → Token 过期 → 访问 info 接口返回 401 → 前端检测到 401 → 自动跳转登录页 → 用户重新登录 → 刷新 Token。
3. **跨模块复用**：收藏模块、浏览历史模块同样需要验证"用户是否登录" → 直接 `Depends(get_current_user)` 一行搞定，无需重复开发认证逻辑。

## 反例/边界（≥1 个）
1. **只做注册不做 Token**：用户注册成功后不返回 Token → 前端无 Token → 所有需要认证的接口都 401 → 用户体验极差，注册完还得手动登录。
2. **密码明文存储**：`User(password=password)` 直接入库 → 数据库一旦泄露，所有用户密码裸奔。必须走 bcrypt 加密。
3. **Token 永不过期**：`expires_at` 设 100 年 → Token 被窃取后攻击者可以永久冒用身份。合理设 7 天，兼顾便利和安全。
4. **修改信息全量覆盖**：忘记 `exclude_none` → 用户只想改简介，结果头像、性别全被更新为 null → 数据丢失。

## 详细解释
**用户模块为后续模块提供的基础设施**：
1. **Token 验证依赖注入**（`get_current_user`）：收藏、浏览历史、评论等模块只需 `Depends(get_current_user)` 即可验证登录
2. **通用成功响应格式**（`success_response`）：所有模块统一返回 `{code, message, data}`
3. **全局异常处理器**：所有模块的错误统一格式接管
4. **密码加密工具**（`utils/security.py`）：可用 `verify_password` 在其他场景做密码二次确认

**用户模块 vs 新闻模块的差异**：
| 维度 | 新闻模块 | 用户模块 |
|------|---------|---------|
| 请求方法 | 全部 GET（读取） | GET + POST + PUT（读写混合） |
| 认证需求 | 无需登录 | 部分接口需 Token 验证 |
| 数据操作 | select 查询为主 | add + update + select |
| 加密需求 | 无 | bcrypt 密码加密 |
| 工程化封装 | 路由 + CRUD | 路由 + CRUD + 通用响应 + 异常处理 + 认证依赖 |
