# 封装缓存操作方法

## 类型判定
procedure — 对 Redis 连接对象的原生方法（`setex` / `get`）做二次封装，增加异常处理、类型转换、序列化等工程化能力。

## 类比 ★
### 一句话比喻
封装缓存操作就像给前台写一本"小黑板使用手册"——不是每次写黑板都重新想"粉笔怎么拿、字写多大"，而是有标准方法：`写(标题, 内容, 保留多久)`、`看(标题)`、`擦(标题)`，出错时自动提示"写黑板失败了，原因是……"。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| `set_cache(k, value, expire)` | 写黑板：标题 = 分区名，内容 = 数据，擦掉时间 = 过期秒数 |
| `get_cache(k)` | 看黑板：按标题找内容，找到就念，找不到就说"没有" |
| `get_json_cache(k)` | 看黑板（复杂版）：内容是表格/清单，念之前先整理成标准格式 |
| `try/except` 异常处理 | 黑板被风吹倒了——有预案，不会整个公司停摆 |
| `json.dumps()` 存前序列化 | 清单贴黑板前先折成一张纸——Redis 只收字符串 |
| `json.loads()` 读后反序列化 | 把折好的纸展开还原成清单——程序能用的格式 |

## 是什么
封装缓存操作方法是对 Redis 连接对象自带方法（`setex` / `get` / `delete` / `exists`）的**二次封装**，目的是：
1. 统一异常处理（`try/except`，失败返回 None/False 而非崩溃）
2. 自动处理数据格式转换（列表/字典 ↔ JSON 字符串）
3. 提供统一的调用接口，业务代码不需要关心底层细节

## 输入-输出空间（程序型必填）
- **输入**：`k: str`（缓存键）、`value: Any`（缓存值）、`expire: int`（过期秒数，默认 3600）
- **输出**：`set_cache` → `True/False`（成功/失败）；`get_cache` → 字符串或 None；`get_json_cache` → 列表/字典或 None
- **前置条件**：已创建 `redis_client` 连接对象（来自 `config/cache.py`）

## 核心代码
```python
# ===== config/cache.py：封装三个核心方法 =====
import json
from typing import Any

# ① 读取普通字符串缓存
async def get_cache(k: str):
    """根据 key 读取缓存（返回字符串），失败返回 None"""
    try:
        return await redis_client.get(k)
    except Exception as e:
        print(f"获取缓存失败：{e}")
        return None

# ② 读取 JSON 格式缓存（列表/字典）
async def get_json_cache(k: str):
    """根据 key 读取缓存并反序列化为列表/字典，失败返回 None"""
    try:
        data = await redis_client.get(k)
        return json.loads(data) if data else None
    except Exception as e:
        print(f"获取 JSON 缓存失败：{e}")
        return None

# ③ 设置缓存（自动处理类型转换）
async def set_cache(k: str, value: Any, expire: int = 3600):
    """写入缓存，自动将列表/字典转 JSON 字符串，成功返回 True，失败返回 False"""
    try:
        if isinstance(value, (dict, list)):
            value = json.dumps(value, ensure_ascii=False)  # ← 保留中文不转义
        await redis_client.setex(k, expire, value)
        return True
    except Exception as e:
        print(f"设置缓存失败：{e}")
        return False
```

| 方法 | Redis 原生方法 | 增强点 |
|------|--------------|--------|
| `get_cache(k)` | `redis_client.get(k)` | +异常捕获，失败返回 None |
| `get_json_cache(k)` | `redis_client.get(k)` | +异常捕获 + `json.loads()` 反序列化 |
| `set_cache(k, v, exp)` | `redis_client.setex(k, exp, v)` | +异常捕获 + 自动 `json.dumps()` + `ensure_ascii=False` |

## 正例（≥2 个）
1. **存字符串**：`await set_cache("greeting", "hello", 600)` → Redis 存的是 `"hello"`，`get_cache("greeting")` → `"hello"`。
2. **存列表/字典**：`await set_cache("categories", [{"id":1, "name":"科技"}], 7200)` → 自动 `json.dumps` 存为 `'[{"id":1,"name":"科技"}]'`，`get_json_cache("categories")` → `[{"id":1, "name":"科技"}]`。
3. **缓存不存在**：`await get_cache("no_such_key")` → 返回 `None`，业务代码用 `if data is None` 判断，走查库逻辑。

## 反例/边界（≥1 个）
1. **不封装直接用原生方法**：每个业务代码都写 `try/except` + `json.loads/dumps`——10 个 CRUD 文件里重复 10 遍，改一行异常处理要改 10 处。
2. **`ensure_ascii=True`（默认）**：中文存成 `\u79d1\u6280` 而非"科技"——Redis 里看到的是乱码，排查问题眼睛疼。
3. **`get_cache` 读 JSON 数据**：如果数据是 `'[{"id":1}]'`（字符串包裹的列表），`get_cache` 返回的还是字符串，不是列表——用错方法导致后续代码 `for item in data` 变成逐字符遍历。

## 详细解释
**三个方法的适用场景**：

| 数据类型 | 写入方法 | 读取方法 |
|---------|---------|---------|
| 纯字符串（如 token、状态码） | `set_cache` | `get_cache` |
| 列表/字典（如新闻列表、分类） | `set_cache`（自动转 JSON） | `get_json_cache`（自动反序列化） |
| 复杂对象（如 ORM 对象） | 先转 dict → `set_cache` | `get_json_cache` |

**为什么过期时间默认 3600 秒？**：1 小时是一个温和的默认值——既不会太频繁过期导致缓存命中率低，也不会太久导致数据陈旧。实际项目中，不同类型数据应设不同过期时间：分类 7200s、列表 600s、详情 1800s、验证码 120s。

**方法暴露的返回值设计**：`set_cache` 返回 `True/False` 供业务层判断是否写成功；`get_cache` / `get_json_cache` 返回 `None` 表示没有/失败，业务层统一用 `if data is None` 判断。
