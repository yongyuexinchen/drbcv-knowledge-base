# 用户登录

## 类型判定
procedure — 四步标准流程：查库验证用户名 → bcrypt 校验密码 → 生成 Token → 返回用户信息。

## 类比 ★
### 一句话比喻
用户登录就像刷卡进门——你输入用户名密码（刷员工卡），门禁系统先在数据库里确认你这个人存在（查用户名），再核对密码是否正确（验密），验证通过后发一张临时门禁卡（Token），以后凭这张卡就能自由进出（访问其他接口）。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| 查用户名是否存在 | 门卫翻员工花名册——"你是我们公司的吗？" |
| bcrypt.verify() 验密 | 门禁比对指纹——"你的指纹和系统里存的一致吗？" |
| 生成 Token | 门卫发临时门禁卡——"拿着这个卡，今天不用再登记了" |
| 401 Unauthorized | 门卫说"你不是我们公司员工"——用户名或密码错误 |
| refresh Token | 续签门禁卡有效期——每次登录刷新7天 |

## 是什么
用户登录接口（POST `/api/user/login`），接收用户名和密码，验证用户名是否存在于数据库，用 bcrypt 的 `verify()` 方法比对明文密码和密文密码是否一致，验证通过后调用 `create_token()` 生成新的访问令牌，返回 Token 和用户信息。

## 输入-输出空间（程序型必填）
- **输入**：`username: str`、`password: str`（通过 Pydantic `UserRequest` 模型校验，复用注册的请求体类型）
- **输出**：`{"code": 200, "message": "登录成功", "data": {"token": "...", "userInfo": {...}}}`
- **前置条件**：已定义 `User` 模型类、已封装 `authenticate_user()` CRUD 方法、已有注册用户

## 核心代码 + 步骤表
```python
# ===== utils/security.py：密码校验方法（注册时已定义） =====
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def verify_password(plain_password: str, hashed_password: str) -> bool:
    """校验明文密码和密文密码是否一致"""
    return pwd_context.verify(plain_password, hashed_password)

# ===== CRUD/users.py：封装登录验证方法 =====
async def authenticate_user(db: AsyncSession, username: str, password: str):
    """验证用户名和密码：成功返回User，失败返回None"""
    # ① 查用户名是否存在
    user = await get_user_by_username(db, username)
    if not user:
        return None

    # ② 验证密码是否正确
    if not verify_password(password, user.password):
        return None

    return user   # 用户名存在且密码正确

# ===== routers/users.py：登录路由 =====
@router.post("/login")
async def login(
    user_data: UserRequest,              # 复用注册的请求体模型
    db: AsyncSession = Depends(get_db)
):
    # ① 验证用户名和密码
    user = await users_crud.authenticate_user(db, user_data.username, user_data.password)
    if not user:
        raise HTTPException(status_code=401, detail="用户名或密码错误")

    # ② 生成 Token
    token = await users_crud.create_token(db, user.id)

    # ③ 构建响应数据
    response_data = UserResponseData(
        token=token,
        user_info=UserInfoResponse.model_validate(user)
    )
    return success_response(message="登录成功", data=response_data)
```

| 步骤 | 代码 | 说明 |
|------|------|------|
| ① 验证用户 | `authenticate_user(db, username, password)` | 查库 → 验密，两步合成一个方法 |
| ② 查用户名 | `get_user_by_username()` | 不存在返回 None |
| ③ 验密 | `verify_password(plain, hashed)` | bcrypt.verify：明文 vs 密文比对 |
| ④ 业务判断 | `if not user: raise HTTPException(401)` | 用户名或密码错误 → 401 未授权 |
| ⑤ 生成 Token | `create_token(db, user.id)` | 登录成功刷新/创建 Token |
| ⑥ 响应结果 | `success_response("登录成功", data)` | 返回 Token + 用户信息 |

## 正例（≥2 个）
1. **正确登录**：用户"大秋"输入密码 123456 → 查库 user 存在 → `verify_password("123456", "$2b$...")` 返回 True → 生成新 Token → 返回 `{"code":200, "message":"登录成功", "data":{...}}`。
2. **用户名不存在**：输入"大秋999" → `get_user_by_username` 返回 None → `authenticate_user` 返回 None → 路由中 `if not user` → raise 401，返回"用户名或密码错误"。
3. **密码错误**：输入正确用户名但密码 654321 → user 存在但 `verify_password` 返回 False → 同样返回 None → 401。

## 反例/边界（≥1 个）
1. **错误信息过于详细**：`"用户名不存在"` vs `"密码错误"` 分开提示 → 攻击者能枚举出哪些用户名是真实注册的。最佳实践是统一返回 `"用户名或密码错误"`，不给攻击者区分线索。
2. **未加密对比**：`if password == user.password` → 数据库存的是密文，永远不等 → 登录永远失败。必须用 `verify_password()` 做 bcrypt 校验。
3. **登录不刷新 Token**：用户已有旧 Token，登录成功但不调用 `create_token()` → Token 有效期不会刷新，可能很快就过期。

## 详细解释
**authenticate_user 的设计模式**：
- 方法内部处理所有验证逻辑（查库 + 验密），返回 User 或 None
- 路由层只管 `if not user: raise`，不需要关心具体是哪个步骤失败
- 遵循"高内聚低耦合"——验证逻辑在 CRUD 层内聚，路由层只管调用和响应

**401 vs 400**：
- 401 Unauthorized：身份认证失败（用户名或密码错误、Token 无效）
- 400 Bad Request：请求本身有问题（用户名重复注册、参数格式错误）
- 登录用 401 更符合 HTTP 语义——"你未通过身份验证"

**登录 vs 注册的代码复用**：
- `UserRequest`：登录和注册共用同一个 Pydantic 请求体模型
- `create_token()`：登录和注册共用一个 Token 生成方法
- `success_response()`：所有接口共用一个响应格式函数
