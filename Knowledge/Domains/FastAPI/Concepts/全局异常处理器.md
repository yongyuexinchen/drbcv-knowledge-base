# 全局异常处理器

## 类型判定
procedure — 两步实现全局接管：定义四类异常处理函数 → `app.add_exception_handler()` 注册到 FastAPI 实例。

## 类比 ★
### 一句话比喻
全局异常处理器就像公司前台统一话术——不管后厨哪个部门炸锅（业务报错、数据库崩溃、未知异常），前台对客人（前端）说的永远是同一套标准回复（`{code, message, data}`），客人不用管内部哪个环节出了问题。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| `app.add_exception_handler()` | 前台培训手册——规定了每种异常该说什么话 |
| `HTTPException` 处理器 | 前台处理"先生您的订单已取消"——标准业务拒绝 |
| 数据库完整性约束处理器 | 前台处理"系统里您的身份证号重复了"——数据冲突 |
| 兜底 `Exception` 处理器 | 前台处理"抱歉系统维护中"——完全意外的故障 |
| `debug_mode=True` | 开发时给技术人员的详细内部故障码——方便排错 |

## 是什么
全局异常处理器是 FastAPI 的异常接管机制：通过 `@app.exception_handler()` 或 `app.add_exception_handler()` 注册异常处理函数，捕获项目中所有未处理的异常（业务层、数据库层、系统层），统一返回 `{code, message, data}` 格式的错误信息，避免异常直接暴露给前端或导致服务崩溃。

## 输入-输出空间（程序型必填）
- **输入**：发生的异常对象（`HTTPException` / `IntegrityError` / `SQLAlchemyError` / `Exception`）
- **输出**：`JsonResponse`，格式为 `{"code": 状态码, "message": "错误描述", "data": null 或 错误详情}`
- **前置条件**：已定义四类异常处理函数

## 核心代码 + 步骤表
```python
# ===== utils/exception.py：第一步，定义四类异常处理函数 =====
from fastapi import Request
from fastapi.responses import JSONResponse
from fastapi.exceptions import HTTPException
from sqlalchemy.exc import IntegrityError, SQLAlchemyError

DEBUG_MODE = True   # 开发模式：返回详细错误信息；上线改为 False

# ① 业务层异常
async def http_exception_handler(request: Request, exc: HTTPException):
    return JSONResponse(
        status_code=exc.status_code,
        content={"code": exc.status_code, "message": exc.detail, "data": None}
    )

# ② 数据库完整性约束异常（唯一性、外键等）
async def integrity_error_handler(request: Request, exc: IntegrityError):
    detail = "数据库约束冲突"
    if DEBUG_MODE:
        detail = {"type": type(exc).__name__, "detail": str(exc), "url": str(request.url)}
    return JSONResponse(
        status_code=400,
        content={"code": 400, "message": "数据库操作失败", "data": detail}
    )

# ③ SQLAlchemy 通用数据库错误
async def sqlalchemy_error_handler(request: Request, exc: SQLAlchemyError):
    detail = None
    if DEBUG_MODE:
        detail = {"type": type(exc).__name__, "detail": str(exc)}
    return JSONResponse(
        status_code=500,
        content={"code": 500, "message": "数据库操作失败", "data": detail}
    )

# ④ 兜底异常：捕获所有未处理的异常
async def generic_exception_handler(request: Request, exc: Exception):
    detail = None
    if DEBUG_MODE:
        detail = {"type": type(exc).__name__, "detail": str(exc), "url": str(request.url)}
    return JSONResponse(
        status_code=500,
        content={"code": 500, "message": "服务器内部错误", "data": detail}
    )

# ===== utils/handlers.py：第二步，批量注册到 FastAPI 实例 =====
def register_exception_handlers(app):
    """一次性注册全部异常处理器（子类在前、父类在后）"""
    app.add_exception_handler(HTTPException, http_exception_handler)      # 业务层
    app.add_exception_handler(IntegrityError, integrity_error_handler)    # 数据完整性
    app.add_exception_handler(SQLAlchemyError, sqlalchemy_error_handler)  # 数据库层
    app.add_exception_handler(Exception, generic_exception_handler)       # 兜底

# ===== main.py：在应用启动时调用 =====
app = FastAPI()
register_exception_handlers(app)   # ← 全局生效
```

| 步骤 | 代码 | 说明 |
|------|------|------|
| ① 定义异常处理函数 | 四个 `async def *_handler(request, exc)` | 每个函数捕获一类异常 |
| ② 注册到实例 | `app.add_exception_handler(异常类, 处理函数)` | 绑定异常类到处理函数 |
| ③ 批量注册 | `register_exception_handlers(app)` | 封装注册逻辑，main 中一行调用 |
| ④ 路由只关注成功 | 路由中只写 `if not user: raise HTTPException(...)` | 异常由全局处理器接管 |

## 正例（≥2 个）
1. **用户名重复注册**：路由中 `raise HTTPException(400, "用户已经存在")` → 被 `http_exception_handler` 捕获 → 返回 `{code:400, message:"用户已经存在", data:null}`。
2. **SQL 语句写错**：CRUD 中 `execute("select * from")`（不小心传了字符串） → 被 `sqlalchemy_error_handler` 捕获 → 返回 `{code:500, message:"数据库操作失败", data:详版错误}`。
3. **新闻详情查不存在的 ID**：路由中 `raise HTTPException(404, "新闻不存在")` → 同样被统一接管，返回标准 404 错误 JSON。

## 反例/边界（≥1 个）
1. **每个路由手写 try/except**：在每个路由函数里包 `try: ... except: return {"code": 500, ...}` → 代码重复、不统一、漏掉某个路由就裸奔。全局异常处理器才是正确做法。
2. **注册顺序不讲究**：如果先注册 `Exception` 再注册 `HTTPException` → `HTTPException` 也是 `Exception` 的子类，会被兜底的 `Exception` 处理器先吃掉，业务错误信息丢失。必须 **子类在前，父类在后**。
3. **上线忘记关 debug_mode**：`DEBUG_MODE = True` 上线 → 攻击者从错误信息中看到数据库表名、SQL 语句、文件路径 → 严重安全漏洞。上线必须改为 `False`。

## 详细解释
**四个异常处理器的覆盖关系**：
```
Exception（兜底）
  ├── SQLAlchemyError（数据库通用）
  │     └── IntegrityError（数据完整性约束：唯一性、外键）
  └── HTTPException（业务层：用户主动抛的）
```

**注册顺序原则**：最具体的子类在前，最抽象的父类在后。FastAPI 按注册顺序匹配，第一个匹配到的处理函数生效。

**异常处理器 vs 路由中的 if 判断**：
- **异常处理器**：规定"错误发生时返回什么格式"——管格式
- **路由中的 if raise**：规定"什么算错误"——管业务规则
- 两者配合：业务规则触发异常 → 异常处理器接管格式 → 统一返回
