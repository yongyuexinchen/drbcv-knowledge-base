## 卡片清单

### 卡片1：客户/服务器模型（C/S）
- **类型**: discriminant
- **概念**: 客户主动请求，服务器被动响应，集中式管理
- **核心特征**: 服务器长期运行等待客户请求；客户需提前知晓服务器IP+端口；客户间不直接通信；便于集中管理但服务器负载大
- **正例**: 百度网盘、DNS、FTP、Email、Web
- **反例/对比**: P2P模型（去中心化、节点间可直接通信）
- **关系**: → [[P2P模型]]

### 卡片2：P2P模型（对等网络）
- **类型**: discriminant
- **概念**: 去中心化，各节点地位平等，节点间可直接通信
- **核心特征**: 任意两台对等方（peer）可直接通信；去中心化；单个节点损坏不影响全局；各节点分摊负载；我为人人，人人为我
- **正例**: BT种子下载（µTorrent）
- **反例/对比**: C/S模型（服务器中心化，客户间不可直接通信）
- **关系**: → [[客户/服务器模型（C/S）]]

### 卡片3：DNS域名系统
- **类型**: connection
- **概念**: 将域名转换为对应IP地址的分布式系统
- **核心流程**: 四类域名服务器（根→顶级→权限→本地）协同工作；递归查询 vs 迭代查询两种方式
- **关键节点**:
  - 根域名服务器：13组全球部署，存储顶级域名服务器IP，仅支持迭代查询
  - 顶级域名服务器：管理二级域名，如.com、.cn
  - 权限域名服务器：存储具体域名→IP映射
  - 本地域名服务器：用户侧默认DNS入口，提供缓存加速
- **关系**: → [[客户/服务器模型（C/S）]]

### 卡片4：FTP文件传输协议
- **类型**: connection
- **概念**: 基于TCP的应用层文件传输协议，采用C/S模型
- **核心流程**: 控制连接（21端口，持久）+ 数据连接（20端口/随机端口，非持久）；主动模式 vs 被动模式
- **关键端口**: 控制连接端口21；主动模式数据连接端口20（固定）
- **关系**: → [[客户/服务器模型（C/S）]]

### 卡片5：电子邮件系统（SMTP/POP3）
- **类型**: connection
- **概念**: 通过SMTP发邮件（push，端口25），通过POP3收邮件（pull，端口110）
- **核心流程**: 用户代理→发送方邮件服务器（SMTP）→接收方邮件服务器（SMTP）→接收方用户代理（POP3/IMAP）
- **关键组件**: 用户代理 + 邮件服务器 + 电子邮件协议
- **关系**: → [[客户/服务器模型（C/S）]]、→ [[MIME]]

### 卡片6：MIME多用途互联网邮件扩展
- **类型**: discriminant
- **概念**: 非协议，是一种格式规范，将非ASCII数据编码为7位ASCII码，使SMTP能传输中文、图片等多媒体内容
- **核心编码**: base64编码（每6比特映射为一个ASCII字符）
- **关系**: → [[电子邮件系统（SMTP/POP3）]]

### 卡片7：万维网WWW与HTTP
- **类型**: mixed（discriminant + connection）
- **子概念**:
  1. URL（统一资源定位符）: protocol://host[:port]/path
  2. HTML（超文本标记语言）: 描述网页结构和内容的标记语言
  3. HTTP（超文本传输协议）: 基于TCP的应用层协议，默认端口80
- **核心流程**: DNS解析→TCP三次握手→HTTP请求/响应→获取HTML→解析并获取引用元素
- **HTTP工作方式**:
  - 非持续连接（HTTP/1.0默认）: 每次请求需新TCP连接，至少2RTT/文件
  - 持续连接非流水线（HTTP/1.1默认）: 串行请求
  - 持续连接流水线: 并行请求，效率最高
- **关系**: → [[客户/服务器模型（C/S）]]

```markdown
# 客户/服务器模型（C/S）

## 类型判定
判别模型 — 回答"一个网络应用属于哪种模型"

## 是什么
客户/服务器模型（C/S模型）是一种网络应用架构，其中服务器长期运行、等待客户请求，客户主动向服务器发出服务请求，服务器被动处理请求并返回结果。服务器处于中心地位。

## 输入-输出空间
- **输入**: 网络应用的架构描述
- **输出**: 是否属于C/S模型
- **映射关系**: 从属关系

## 正例（至少2个）
1. **百度网盘**: 你的电脑/手机安装客户端，百度公司部署网盘服务器，客户端向服务器请求下载/上传文件
2. **Web访问**: 浏览器（客户端）向Web服务器（端口80）请求网页数据

## 反例/边界（至少1个）
1. **常见误解**: C/S模型中客户和服务器地位平等？不，服务器处于中心地位，地位不平等。客户进程之间不直接通信，必须通过服务器中转

## 详细解释
C/S模型的典型工作流程：服务器长期运行等待客户请求 → 客户主动向服务器发出服务请求（需提前知晓服务器IP+端口） → 服务器被动处理请求并返回结果。服务器不需要提前知道客户端的地址，因为收到请求后可获知客户IP和端口。

**优点**: 便于集中管理（数字资源、带宽等统一管控）
**缺点**: 服务器损坏影响全局；服务器负载大，性能决定系统整体性能

## 细节备注

### 子特性
| 特性 | 说明 |
|------|------|
| 通信方向 | 客户→服务器：主动请求；服务器→客户：被动响应 |
| 地位关系 | 不平等，服务器处于中心地位 |
| 客户间通信 | 不直接通信，需通过服务器中转 |
| 地址知晓 | 客户需提前知晓服务器IP+端口；服务器不需提前知晓客户地址 |

### 使用原则
- DNS、FTP、电子邮件、Web应用都是典型的C/S模型
- 服务器长期运行待命，随时可能被新客户访问

## 关系
### → 指向
- [[P2P模型]] (对等网络模型是C/S的去中心化对立方案)
### ← 被指向
- [[DNS域名系统]] (DNS是典型C/S模型应用)
- [[FTP文件传输协议]] (FTP采用C/S模型)
- [[电子邮件系统（SMTP/POP3）]] (电子邮件协议采用C/S模型)
- [[万维网WWW与HTTP]] (Web访问是C/S模型)
```

```markdown
# P2P模型（对等网络）

## 类型判定
判别模型 — 回答"一个网络应用属于哪种模型"

## 是什么
P2P模型（对等网络模型）是一种去中心化的网络应用架构，各主机（称为对等方peer）之间地位平等，任意两台主机可以直接通信。核心思想是去中心化——"我为人人，人人为我"。

## 输入-输出空间
- **输入**: 网络应用的架构描述
- **输出**: 是否属于P2P模型
- **映射关系**: 从属关系

## 正例（至少2个）
1. **BT种子下载（µTorrent）**: 一台主机拥有资源后做成BT种子发布，其他主机通过种子从所有拥有该资源的主机同时索取数据，下载速度随分享者增多而加快
2. **P2P文件共享应用**: 多台对等方同时为下载者传输文件的不同部分，合并成完整文件

## 反例/边界（至少1个）
1. **常见误解**: P2P模型没有缺点？不，P2P也有缺点：主机在被服务的同时需要给其他主机服务导致负载较大；去中心化导致网络数据流量不可控，易造成拥塞；频繁读写硬盘可能缩短寿命

## 详细解释
P2P模型的核心特点是**去中心化**：

- 任两台对等方之间可直接通信（C/S模型中客户间不能直接通信）
- 单个节点损坏不影响全局（其他节点仍可提供服务）
- 各节点分摊负载，下载者越多下载速度越快

**优点**: 单个节点损坏不影响全局；各节点分摊负载，下载速度快
**缺点**: 主机在享受服务的同时需为他人服务，负载较大；数据流量不可控，易导致网络拥塞；硬盘频繁读写影响寿命

## 细节备注

### 子特性
| 特性 | 说明 |
|------|------|
| 地位关系 | 平等，去中心化 |
| 节点间通信 | 任意对等方可直接通信 |
| 负载特点 | 同时在服务他人和被他人服务 |
| 抗风险性 | 单个节点损坏不影响全局 |

### 使用原则
- ISP（互联网服务提供商）通常讨厌P2P应用，因其流量大且不可管控
- 现实中的P2P应用可能被反对，原因包括硬盘损耗和网络拥塞

## 关系
### → 指向
- [[客户/服务器模型（C/S）]] (C/S是P2P的对立架构方案)
### ← 被指向
- （无常用子概念指向P2P）
```

```markdown
# DNS域名系统

## 类型判定
连接模型 — 回答"域名如何一步步解析为IP地址"

## 是什么
DNS（域名系统）是一种将层次结构的域名转换为对应IP地址的分布式系统。它由四类域名服务器协同工作，通过递归查询或迭代查询完成域名解析。

## 输入-输出空间
- **输入**: 一个域名（如 www.qq.com）
- **输出**: 对应的IP地址
- **映射关系**: 映射关系（域名 → IP地址）

## 正例（至少2个）
1. **访问网站**: 用户在浏览器输入 www.qq.com，DNS通过层次化查询最终返回该域名对应的服务器IP地址
2. **本地缓存命中**: 本地域名服务器缓存中有 www.bilibili.com 的记录，直接返回IP，无需逐级查询根域名服务器

## 反例/边界（至少1个）
1. **常见误解**: DNS查询每次都要从根域名服务器开始？不，本地域名服务器有缓存，大多数查询可直接由缓存命中返回，无需打扰根域名服务器

## 详细解释
### 四类域名服务器
1. **根域名服务器**: 全球13组，存储所有顶级域名服务器的IP地址，仅支持迭代查询；通过任播技术实现就近访问和冗余容灾
2. **顶级域名服务器**: 管理.com、.cn等顶级域名下的权限域名服务器信息
3. **权限域名服务器**: 存储具体域名与IP地址的映射关系（最终答案所在）
4. **本地域名服务器**: 用户侧默认DNS入口（通过DHCP配置）；内部有DNS缓存，减少向根服务器的查询频率

### 两种查询方式
**递归查询**: "你问我问题，即便我不知道最终答案，也会想方设法的帮你找到最终答案"
- 本地域名服务器问根域名服务器 → 根问顶级 → 顶级问权限 → 返回结果逐层回传
- 终端主机只需发1次查询，本地域名服务器对外也只发1次

**迭代查询**: "你问我问题，如果我不知道最终答案，就告诉你下一个该问谁"
- 本地域名服务器问根 → 根告诉"去问顶级" → 本地问顶级 → 顶级告诉"去问权限" → 本地问权限 → 获得答案
- 本地域名服务器需发多次查询（最多3次：根→顶级→权限）

### 缓存机制
- **本地域名服务器缓存**: 降低对根域名服务器的查询频率
- **主机解析器缓存**: 降低对本地域名服务器的查询频率
- 缓存设置TTL（有效时间），过期后需重新查询

## 细节备注

### 子特性
| 特性 | 说明 |
|------|------|
| 传输层协议 | 基于UDP（端口53） |
| 应用层模型 | C/S模型 |
| 任播技术 | 同一组根域名服务器的多台主机共享一个IP，报文就近投递 |
| 解析器 | 主机内部负责发出DNS查询报文和解析响应报文的程序 |

### 历年真题要点
- 2010年40题：递归方法下，用户主机和本地域名服务器各只发1次DNS查询请求
- 2016年40题改编：迭代查询下，本地域名服务器对外最少发0次（缓存命中），最多发3次

## 关系
### → 指向
- [[客户/服务器模型（C/S）]] (DNS是典型的C/S模型应用)
### ← 被指向
- [[万维网WWW与HTTP]] (访问网页的第一步就是DNS解析)
```

```markdown
# FTP文件传输协议

## 类型判定
连接模型 — 回答"FTP客户端和服务器之间如何一步步完成文件传输"

## 是什么
FTP（文件传输协议）是一种基于TCP的应用层协议，采用C/S模型，通过控制连接和数据连接两条独立的TCP连接实现文件上传和下载。控制信息与数据信息分离传输（带外传输）。

## 输入-输出空间
- **输入**: 用户想要上传或下载的文件请求
- **输出**: 文件在客户端和服务器之间的成功传输
- **映射关系**: 映射关系（文件传输请求 → 文件传输结果）

## 正例（至少2个）
1. **下载文件**: 客户端通过控制连接（21端口）登录服务器，请求下载文件；服务器通过数据连接（主动模式20端口，或被动模式随机端口）传输文件数据
2. **上传文件**: 客户端通过控制连接登录并请求上传，通过数据连接将本地文件传输到服务器指定目录

## 反例/边界（至少1个）
1. **常见误解**: FTP可以直接修改远程文件的某一部分？不，FTP只能整体下载修改后再整体上传，无法局部修改文件

## 详细解释
### 两次连接
1. **控制连接**（TCP，21端口）
   - 持久连接，整个FTP会话期间保持不断
   - 用于传输控制信息（登录命令、用户名密码、操作指令等）
   - 不传输文件数据
   
2. **数据连接**（TCP，20端口或随机端口）
   - 非持久连接，每次文件传输前建立，传输完成后立即关闭
   - 用于传输文件数据以及文件列表信息
   - 数据传送进程随数据连接的建立而创建，随关闭而销毁

### 两种传输模式
**主动模式**（官方默认，考研默认）：
- 客户端告诉服务器自己的IP+随机端口 → 服务器通过20端口主动连接客户端
- 现实问题：无法穿透NAT（内网环境服务器无法主动连接客户端）

**被动模式**（现实默认）：
- 服务器开放随机端口并告知客户端 → 客户端主动连接服务器的随机端口
- 更适应NAT环境

### 三个阶段
1. **登录阶段**: 客户端控制进程连接服务器21端口 → 主进程建立TCP连接后继承给控制进程 → 客户端发送用户名密码 → 服务器验证
2. **数据传输阶段**: 客户端指定主动/被动模式 → 发送上传/下载请求 → 建立数据连接 → 传输文件 → 断开数据连接
3. **登出阶段**: 客户端发送quit命令 → 服务器响应 → 断开控制连接（四次挥手）

### 带外传输
控制信息用独立的数据连接传输，称为"带外传输"。优点是控制命令不会因大数据传输而阻塞——即使正在下载大文件，也可通过控制连接随时发送停止命令。

## 细节备注

### 子特性
| 特性 | 说明 |
|------|------|
| 传输层协议 | 基于TCP |
| 应用层模型 | C/S模型 |
| 控制连接端口 | 21（固定） |
| 数据连接端口（主动） | 20（固定） |
| 数据连接端口（被动） | 随机端口 |
| 控制连接特性 | 持久 |
| 数据连接特性 | 非持久（一次性的） |
| 通信方式 | 带外传输（控制信息与数据信息分离） |

### 使用原则
- 查看文件列表（list命令）通过控制连接发送请求，但文件列表数据通过数据连接传输
- 默认模式（考研）：主动模式
- 现实默认：被动模式（可穿透NAT）

## 关系
### → 指向
- [[客户/服务器模型（C/S）]] (FTP是典型的C/S模型)
### ← 被指向
- （无）
```

```markdown
# 电子邮件系统（SMTP/POP3）

## 类型判定
连接模型 — 回答"一封邮件从发件人到收件人经过哪些步骤完成传送"

## 是什么
电子邮件系统由用户代理、邮件服务器和电子邮件协议三部分组成。SMTP（简单邮件传输协议，端口25）用于发送邮件，采用push方式；POP3（邮局协议第3版，端口110）用于接收邮件，采用pull方式。两个协议均采用C/S模型。

## 输入-输出空间
- **输入**: 发件人撰写的邮件（收件人、主题、正文）
- **输出**: 收件人在用户代理上成功阅读邮件
- **映射关系**: 映射关系（发送邮件 → 接收邮件）

## 正例（至少2个）
1. **QQ邮箱→网易邮箱**: 用户在QQ邮箱APP写邮件发给163邮箱 → SMTP推送到QQ邮件服务器 → SMTP推送到网易邮件服务器 → 收件人通过POP3从网易服务器拉取邮件
2. **SMTP工作过程**: 发送方邮件服务器（SMTP客户端）→ 接收方邮件服务器（SMTP服务器），经过hello→mail from→rcpt to→data→quit命令序列完成邮件传输

## 反例/边界（至少1个）
1. **常见误解**: POP3和SMTP都能发邮件？不，POP3只能接收/读取邮件，不能发送邮件。发邮件只能使用SMTP协议（现代系统也可用HTTP/HTTPS发邮件）

## 详细解释
### 三大组成部分
1. **用户代理**: 邮件APP（QQ邮箱、网易邮箱等），提供编写/发送/接收邮件的界面
2. **邮件服务器**: 存放用户邮件，负责发送和接收邮件；可同时扮演SMTP客户端和SMTP服务器
3. **电子邮件协议**: SMTP（发）+ POP3（收）

### 邮件传输流程
发件人用户代理 → SMTP推送 → 发送方邮件服务器 → SMTP推送 → 接收方邮件服务器 → POP3拉取 → 收件人用户代理

### SMTP工作过程（发送方→接收方）
1. TCP三次握手连接25端口
2. 发送hello命令
3. 发送mail from（指明发件人）
4. 发送rcpt to（指明收件人，服务器检查收件人是否存在）
5. 发送data命令（开始传输邮件内容）
6. 传输邮件首部+主体
7. 发送quit命令 → 断开TCP连接

### POP3工作过程（收件人→服务器）
1. TCP三次握手连接110端口
2. 发送用户名密码验证身份
3. 请求查看邮件列表
4. 请求下载邮件内容
5. 两种下载方式：下载并删除服务器上的邮件 / 下载但保留服务器上的邮件

### 电子邮件的格式
- **信封**: 给SMTP协议使用的数据结构（指明谁发的、发给谁），用户代理自动生成
- **内容**: 首部（收件人to、发件人from、主题subject，其中to和from必填，subject可选）+ 主体（正文）

### 通信特点
- SMTP：push（推送）方式，客户端主动推给服务器
- POP3：pull（拉取）方式，客户端主动请求服务器返回邮件

## 细节备注

### 子特性
| 特性 | 说明 |
|------|------|
| SMTP端口 | 25 |
| POP3端口 | 110 |
| SMTP通信方式 | push（推） |
| POP3通信方式 | pull（拉） |
| SMTP传输限制 | 只能传7位ASCII码 |
| 应用层模型 | C/S模型 |
| IMAP协议 | POP3的进阶版，也用于收邮件，功能更丰富 |

### 补充
- 邮件服务器有邮件缓存（队列），先来先服务
- 现代邮件系统常用HTTP/HTTPS替代SMTP和POP3进行收发
- SMTP的mail from和rcpt to命令携带的就是信封信息

## 关系
### → 指向
- [[客户/服务器模型（C/S）]] (电子邮件协议均采用C/S模型)
- [[MIME]] (MIME解决SMTP只能传ASCII的限制)
### ← 被指向
- （无）
```

```markdown
# MIME多用途互联网邮件扩展

## 类型判定
判别模型 — 回答"MIME是一个协议还是一种格式规范"

## 是什么
MIME（多用途互联网邮件扩展）不是通信协议，而是一种格式规范。它解决了SMTP只能传输7位ASCII码（纯英文+符号）的限制，通过编码将中文、图片、视频等非ASCII数据转换为7位ASCII码，使得SMTP可以传输丰富多媒体内容的邮件。

## 输入-输出空间
- **输入**: 非ASCII数据（中文、图片、视频等二进制数据）
- **输出**: 编码后的7位ASCII码文本
- **映射关系**: 映射关系（非ASCII数据 → ASCII编码数据，解码时逆向还原）

## 正例（至少2个）
1. **中文邮件**: 中文文本通过base64编码转换为纯ASCII字符串，SMTP传输后在接收端解码还原为中文
2. **图片附件**: JPEG图片的二进制数据通过base64编码为ASCII字符串，SMTP传输后解码还原为图片

## 反例/边界（至少1个）
1. **常见误解**: MIME是一个通信协议？不，MIME不是协议，它只是对邮件格式的扩展规范。它定义了邮件内容的格式和编码方式，不负责通信本身

## 详细解释
MIME主要包括三部分内容：

1. **五个新的邮件首部字段**: 在SMTP原有to/from/subject基础上新增，如MIME-Version（版本号，确保编解码规则一致）等

2. **多种邮件主体格式**: 定义不同类型内容的格式规范
   - Content-Type: text（文本）/ image（图片）/ video（视频）等
   - Content-Transfer-Encoding: 指明编码方式
   - 用分界线（boundary）分隔不同的内容部分

3. **传送编码**: 最著名的是base64编码
   - 原理：每6比特为一组（2^6=64种状态），映射为64个不同的ASCII字符
   - 类比16进制（每4比特映射为一个16进制字符），base64是"64进制"
   - 将二进制数据编码为纯ASCII字符串

### 工作流程
非ASCII数据 → MIME编码为7位ASCII码 → SMTP传输 → MIME解码还原为原始数据

## 细节备注

### 子特性
| 特性 | 说明 |
|------|------|
| 本质 | 格式规范，非协议 |
| 核心编码 | base64（6比特→1个ASCII字符） |
| 解决的根本问题 | SMTP仅能传输7位ASCII码 |
| 角色类比 | 翻译官：把非ASCII数据"翻译"成ASCII，让SMTP能传输 |

### 使用原则
- MIME版本在发送方和接收方之间要对齐，确保编解码规则一致
- base64是一种"64进制"编码，与16进制是类比关系

## 关系
### → 指向
- [[电子邮件系统（SMTP/POP3）]] (MIME作为SMTP的扩展，解决其ASCII限制)
### ← 被指向
- （无）
```

```markdown
# 万维网WWW与HTTP

## 类型判定
混合模型 — URL和HTML是判别型（回答"是什么"）；HTTP工作流程是连接型（回答"访问网页时一步步发生什么"）

## 是什么
万维网（WWW）是一个全球范围的分布式连接式信息存储空间。三大组成元素为URL（统一资源定位符）、HTTP（超文本传输协议）、HTML（超文本标记语言）。HTTP基于TCP，默认端口80，采用C/S模型。

## 输入-输出空间
- **输入**: 用户在浏览器输入的URL（域名或IP）
- **输出**: 浏览器渲染出的完整网页
- **映射关系**: 映射关系（URL请求 → 网页显示）

## 正例（至少2个）
1. **访问B站**: 浏览器输入 www.bilibili.com → DNS解析获取IP → TCP三次握手 → HTTP请求首页HTML → 解析HTML并请求引用的图片/视频等元素 → 渲染显示完整页面
2. **并行获取元素**: 持续连接流水线模式下，浏览器一次发出多个HTTP请求获取HTML中引用的多个元素，提高加载效率

## 反例/边界（至少1个）
1. **常见误解**: TLS加密的HTTPS是完全不同的协议？不，HTTPS是HTTP的"Pro Max Ultra版"，在HTTP基础上增加了加密功能，基本原理相同

## 详细解释
### 三大组成元素
1. **URL（统一资源定位符）**: `protocol://host[:port]/path`
   - protocol: 通信协议（http/https）
   - host: 服务器域名或IP地址
   - port: 默认为80（可省略）
   - path: 资源路径（访问首页时可省略，服务器返回默认首页index.html）

2. **HTML（超文本标记语言）**: 用标签（如h1、img、video）描述网页结构和内容
   - 一个网页 = 1个HTML文件 + N个网页元素（图片、视频、音频等）
   - HTML中指明元素存储路径，浏览器根据路径获取并渲染

3. **HTTP（超文本传输协议）**: 基于TCP，默认端口80，C/S模型
   - 两种报文：请求报文 + 响应报文
   - HTTP请求通常体积小（只包含请求信息），而HTTP响应可能体积大（携带文件数据）

### 访问网页的完整流程
1. **DHCP配置**: 主机获取IP、子网掩码、默认网关、DNS服务器地址
2. **DNS解析**: 浏览器构造DNS请求报文（UDP，端口53）→ 本地域名服务器查询 → 返回域名对应IP
3. **TCP三次握手**: 浏览器与Web服务器（IP:80）建立TCP连接
4. **HTTP请求/响应**: 第三次握手携带HTTP请求（GET /index.html）→ 服务器返回HTTP响应（携带HTML文件）
5. **解析HTML**: 浏览器解析HTML，发现引用的元素（图片、视频等）
6. **获取引用元素**: 对每个元素发起HTTP请求/响应，根据HTTP工作方式不同而不同

### HTTP的三种工作方式
1. **非持续连接（HTTP/1.0默认）**: 每次HTTP请求/响应后立即断开TCP连接，获取N个文件需N次TCP连接；每个文件至少需要2×RTT时间；可并行建立TCP连接加速

2. **持续连接非流水线（HTTP/1.1默认）**: TCP连接保持，串行发出请求（获得一个响应后再请求下一个）

3. **持续连接流水线**: TCP连接保持，浏览器一次连续发出所有请求，服务器连续返回所有响应；效率最高

## 细节备注

### 子特性
| 特性 | 说明 |
|------|------|
| HTTP默认端口 | 80 |
| 应用层模型 | C/S模型 |
| 传输层协议 | 基于TCP |
| HTTP/1.0默认方式 | 非持续连接 |
| HTTP/1.1默认方式 | 持续连接（可用Connection: close切换为非持续） |
| 请求报文特点 | 体积小（仅包含请求信息） |
| 响应报文特点 | 可能体积大（携带文件数据），传输时延不可忽略 |

### 关键术语
- **RTT**: 往返时间，衡量从请求发出到收到响应的时间
- **非持续连接**: 每次请求/响应后立即释放TCP连接
- **并行TCP连接**: 同时建立多个TCP连接并发获取文件，提高效率（但第一个HTML文件必须串行获得后才能知道需引用哪些元素）

## 关系
### → 指向
- [[客户/服务器模型（C/S）]] (Web访问是经典的C/S模型)
- [[DNS域名系统]] (访问网页第一步是DNS解析域名)
### ← 被指向
- （无）
```
