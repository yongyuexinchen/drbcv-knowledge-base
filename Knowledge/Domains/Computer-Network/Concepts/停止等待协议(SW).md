# 停止等待协议(SW)

## 类型判定
连接型 — 回答"停止等待协议如何运作"，涉及发—等—确认—发下一帧的完整流程，以及超时重传的异常处理逻辑。

## 是什么
停止等待协议（Stop-and-Wait，SW）是最简单的可靠传输协议。其核心规则是：**发送方每发送一个数据帧，就停止等待接收方的确认帧（ACK），收到确认后再发送下一帧**。发送窗口和接收窗口的大小均为1。它需要配合**帧编号**（1比特即可，编号0/1循环）、**确认机制**和**超时重传机制**，以解决数据帧丢失、数据帧出错和确认帧丢失等问题，实现流量控制和可靠传输。

## 输入-输出空间
- **输入**：网络层交下来的数据（分组）+ 接收方反馈的ACK
- **输出**：发送数据帧、接收确认帧、超时后重传帧
- **映射关系**：映射关系 — 发送方行为由"是否收到当前帧的ACK"决定

## 正例（至少2个）
1. **正常无差错传输**：发送方发DATA0→接收方收下返回ACK0→发送方收到ACK0后发DATA1→接收方返回ACK1→如此交替。每次只发一帧，等确认后才发下一帧。
2. **数据帧丢失后超时重传**：发送方发DATA0后启动计时器，数据帧中途丢失未到达接收方。计时器超时→发送方重传DATA0。接收方收到后返回ACK0，通信恢复正常。

## 反例/边界（至少1个）
1. **确认帧丢失导致重复帧**：发送方发DATA1并收到ACK1，但ACK1中途丢失。发送方超时重传DATA1，接收方收到后看到编号1不在当前窗口内（窗口已滑到期待0号帧）→丢弃重复帧，重新返回ACK1。发送方收到重复的ACK1后确认DATA1已收到。

## 详细解释

### 协议四要素
| 要素 | 停止等待协议的设定 |
|------|------------------|
| **滑动窗口** | WT=1, WR=1 |
| **确认机制** | 每收到一个正确帧，返回该帧的ACK |
| **重传机制** | 超时重传（发送时启动计时器，超时未收到ACK即重传） |
| **帧编号** | 1比特，编号0/1循环（满足 WT+WR ≤ 2¹ =2） |

### 正常传输过程
```
发送方        接收方
  |---DATA0---→|  数据帧发送
  |←---ACK0----|  确认帧返回
  |---DATA1---→|  下一个数据帧
  |←---ACK1----|  确认
  |---DATA0---→|  编号循环
  ...
```

### 三种异常情况及处理
| 异常情况 | 表现 | 处理方式 |
|---------|------|---------|
| **数据帧丢失** | 发送方超时未收到ACK | 超时重传当前帧 |
| **数据帧出错** | 接收方CRC校验失败，丢弃帧 | 发送方超时后重传 |
| **确认帧丢失** | 接收方已收数据帧，但ACK丢失 | 发送方超时重传→接收方丢弃重复帧→重新返回ACK |

### 流量控制原理
只有接收窗口向后滑动并返回ACK后，发送窗口才能向右滑动。接收方控制了发送窗口的滑动速度，从而控制发送速率。

### 信道利用率
理想情况下信道利用率公式：
```
U = TD / (TD + RTT + TA)
```
- TD：数据帧传输时延
- RTT：两倍单向传播时延
- TA：确认帧传输时延

由于每发一帧都要等一轮确认，停止等待协议的信道利用率较低（尤其当传播时延远大于传输时延时）。

## 生活类比
就像**寄快递时"签收确认"**——你寄一个包裹，必须等快递员打电话说"签收确认了"，你才寄下一个。如果电话一直没来（快递丢了），你就打电话追问（重寄）。如果快递员回电话说"收到了"但你没听清（确认帧丢失），你也会再寄一次——快递员会说"收过了，别重复寄"（丢弃重复帧并把签收单再传一遍）。
