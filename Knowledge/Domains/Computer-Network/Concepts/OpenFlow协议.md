# OpenFlow 协议

## 类型判定
判别型 — 回答"OpenFlow 是什么、流表如何工作、三种消息类型各自干什么"，核心是区分 OpenFlow 作为 SDN **南向接口协议**的定位，以及流表匹配-动作的执行逻辑。

## 类比
**一句话比喻：** OpenFlow 就是 SDN 控制器遥控交换机的「万能遥控器协议」——控制器说"凡是来自 A、去往 B 的视频流量，从 3 号口转发出去"，交换机就照做，自己不动脑。

| 维度 | 生活映射 |
|------|---------|
| 流表 | 快递分拣中心的《分拣规则手册》——"凡是寄往北京的快件 → 丢进 3 号传送带" |
| 匹配域（12 元组） | 快递单上的所有字段：寄件人、收件人、地址、电话、重量、类别……逐项核对 |
| Table-Miss | 手册最后一行："以上都不匹配的 → 打电话问经理（送交控制器）" |
| 三种消息类型 | 老板下命令（Controller-to-Switch）、员工打报告（Asynchronous）、日常打招呼（Symmetric） |

## 是什么
OpenFlow 是 SDN 架构中**控制器与交换机之间的标准化南向接口协议**，由 ONF（开放网络基金会）制定。它定义了两件事：（1）**流表**的数据结构——控制器如何描述转发规则；（2）**通信协议**——控制器和交换机之间如何下发流表、上报事件、维持连接。

**核心思想**：交换机不再自己计算路由表，而是从控制器接收**流表**，对每个到达的分组按流表中的规则进行**匹配 → 执行动作**。

## 输入-输出空间
- **输入**：控制器下发的流表规则（匹配域 + 优先级 + 动作）
- **输出**：交换机对每个分组的处理结果（转发到某端口 / 丢弃 / 修改字段 / 送交控制器）
- **映射关系**：映射关系 — 流表将「分组特征（12 元组）」映射到「处理动作」

## OpenFlow 流表

流表是 OpenFlow 交换机的核心数据结构，由多条**流表项**组成。交换机收到分组后，从流表的第一条开始按优先级匹配，执行第一条匹配成功的规则。

### 流表项结构

| 组成部分 | 说明 |
|---------|------|
| **匹配域（Match Fields）** | 定义"什么样的分组匹配这条规则"，最多可匹配 12 个字段（12 元组） |
| **优先级（Priority）** | 数字越大优先级越高，多条匹配时优先执行高优先级规则 |
| **计数器（Counters）** | 统计匹配了多少分组/多少字节，用于流量监控 |
| **指令（Instructions）** | 匹配后执行的动作：转发、丢弃、修改、跳转到另一张流表 |
| **超时（Timeouts）** | 硬超时（hard_timeout）和空闲超时（idle_timeout），过期自动删除 |
| **Cookie** | 控制器用来标记/过滤流表项的标识符 |

### 匹配域 12 元组（考研重点）

| # | 字段 | 说明 | # | 字段 | 说明 |
|---|------|------|---|------|------|
| 1 | **入端口** | 从哪个物理端口进来 | 7 | IP 协议号 | TCP=6 / UDP=17 / ICMP=1 |
| 2 | 源 MAC | 发送方 MAC 地址 | 8 | IP ToS | 服务类型（QoS） |
| 3 | 目的 MAC | 接收方 MAC 地址 | 9 | **源端口（TCP/UDP）** | 发送方传输层端口 |
| 4 | 以太网类型 | 0x0800=IPv4 / 0x0806=ARP | 10 | **目的端口（TCP/UDP）** | 接收方传输层端口 |
| 5 | **源 IP** | 发送方 IP 地址 | 11 | MPLS 标签 | 多协议标签交换 |
| 6 | **目的 IP** | 接收方 IP 地址 | 12 | 源/目的 IP + 端口 | 完整五元组匹配 |

> **考研记忆技巧**：12 元组 = **L1（入端口）→ L2（MAC + EtherType）→ L3（IP + 协议 + ToS）→ L4（端口）**，逐层往上，覆盖了从物理层到传输层的所有关键标识字段。实际最常用的是 **L2~L4 五元组**（源/目的 IP + 源/目的端口 + 协议）。

### 动作（Actions）分类

| 动作类型 | 说明 | 示例 |
|---------|------|------|
| **转发（Output）** | 从指定端口发出 | 匹配到某流 → Output: Port 3 |
| **丢弃（Drop）** | 不转发，直接丢弃 | 匹配到黑名单流 → Drop |
| **修改字段（Set-Field）** | 修改分组的某个字段值 | Set-Field: 目的 IP = 10.0.0.2（NAT 效果） |
| **送交控制器** | 发到控制器处理 | Table-Miss → 封装为 Packet-In 消息送控制器 |
| **跳转（Goto-Table）** | 跳到下一张流表继续处理 | 多级流表流水线 |

### Table-Miss 表项

每条流表的**最低优先级规则**，匹配"前面所有规则都没命中"的分组。三种处理方式：

| 方式 | 行为 |
|------|------|
| **送交控制器** | 封装为 Packet-In 消息发送给控制器（控制器决策后下发新流表项） |
| **直接丢弃** | 不匹配任何规则的未知流量直接丢掉 |
| **转发到某端口** | 作为兜底默认路由 |

> 典型场景：SDN 交换机刚启动时流表为空 → 所有分组触发 Table-Miss → 送控制器 → 控制器计算后下发精确流表项 → 后续同类分组线速转发。

## 三种消息类型

| 类型 | 方向 | 作用 | 代表消息 |
|------|------|------|---------|
| **Controller-to-Switch** | 控制器 → 交换机 | 控制器主动管理交换机 | **Flow-Mod**（增删改流表）、**Packet-Out**（指示交换机转发某分组）、Barrier（确认操作完成） |
| **Asynchronous（异步）** | 交换机 → 控制器 | 交换机主动上报事件 | **Packet-In**（Table-Miss/送控制器）、Flow-Removed（流表项过期通知）、Port-Status（端口状态变化） |
| **Symmetric（对称）** | 双向 | 连接维护 | **Hello**（握手协商版本）、Echo Request/Reply（心跳保活） |

### 关键交互流程

```
1. TCP 三次握手 (端口 6653)
2. Hello 消息（双方协商 OpenFlow 版本）
3. Feature Request/Reply（控制器询问交换机能力：端口数、流表数量、支持的动作）
4. 控制器下发 Flow-Mod（添加初始流表）
5. 正常运行：
   - 交换机匹配流表转发分组
   - Table-Miss → Packet-In 上报控制器
   - 控制器 → Packet-Out / Flow-Mod 回应
6. Echo Request/Reply 维持心跳
```

## OpenFlow 版本演进

| 版本 | 年份 | 关键变化 |
|------|------|---------|
| **1.0** | 2009 | 首版：单级流表、12 元组、IPv4 为主 |
| **1.1** | 2011 | 引入**多级流表**（流水线处理）和 Group Table |
| **1.3** | 2012 | 支持 IPv6、多控制器、计量表（Meter Table）；**目前最广泛部署** |
| **1.4/1.5** | 2013-2015 | 同步机制优化、出口表、数据包类型感知 |

> **考研通常以 1.0 和 1.3 为主**：1.0 理解基本概念，1.3 了解多级流表和 IPv6 支持。

## 正例（≥2个）

1. **SDN 实现访问控制**：管理员通过北向接口配置策略"禁止财务部访问外网" → SDN 控制器生成流表项"匹配: 源IP=财务部网段 + 目的IP=外网 → 动作: Drop" → 通过 OpenFlow Flow-Mod 消息下发到接入交换机 → 财务部发出外网请求 → 交换机匹配流表 → 直接丢弃。
2. **Table-Miss 触发流表学习**：一个新主机 A 向主机 B 发数据 → 交换机流表中无匹配规则 → 触发 Table-Miss → Packet-In 上报控制器 → 控制器知道 A 和 B 的 MAC 地址及所在端口 → 生成两条流表项分别下发 → 后续 A↔B 通信直接在交换机线速转发，无需再经控制器。

## 反例/边界（≥1个）

1. **OpenFlow 交换机 ≠ 传统交换机**：传统交换机通过**自学习**（记录源 MAC+端口）构建 MAC 地址表，独立决策；OpenFlow 交换机自己不学习、不决策，**完全依赖控制器下发的流表**。如果把控制器断开，OpenFlow 交换机要么走 Table-Miss（但控制器不可达，丢包），要么依赖已有的流表继续转发（但无法应对新流）。

## 细节备注

### 考研常见考点

| 考点 | 答案 |
|------|------|
| OpenFlow 是 SDN 的什么？ | **南向接口协议** |
| OpenFlow 交换机依据什么转发？ | **流表**（flow table），而非传统路由表 |
| 流表比传统路由表精细在哪？ | 传统路由表只看 IP 目的地址；流表可匹配**从 L1 到 L4 的 12 个字段** |
| 不匹配任何流表怎么办？ | Table-Miss → Packet-In 送交控制器 |
| OpenFlow 使用什么传输层协议？ | **TCP**（端口 6653，早期用 6633） |

### OpenFlow 的局限

1. **控制器是瓶颈**：Table-Miss 触发的大量 Packet-In 可能压垮控制器
2. **流表容量有限**：TCAM 硬件流表条目有限（通常几千到几万条）
3. **不是唯一南向协议**：P4、NETCONF/YANG 等也是 SDN 南向方案
