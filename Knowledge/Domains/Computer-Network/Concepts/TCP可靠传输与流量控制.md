# TCP可靠传输与流量控制

## 类型判定
连接型 — 回答"TCP如何保证数据传输的可靠性和控制发送速率"，涉及序号编号、确认机制（含累计确认/捎带确认/推迟确认/立即确认）、超时重传和快重传的完整工作流程，以及发送窗口和接收窗口的滑动逻辑。

## 是什么
TCP通过**序号 + 确认 + 重传**三大机制实现可靠传输，通过**滑动窗口**实现流量控制。每个字节都有唯一的序号，接收方通过确认号告知发送方哪些字节已收到；发送方设置超时重传计时器，未收到确认则重传。流量控制方面，接收方通过**接收窗口（RWND）** 告知自身剩余接收能力，发送方的**发送窗口**不能超过接收窗口大小，从而控制发送速率。快重传是重传机制的优化：连续收到3个冗余ACK时立即重传，不等待超时。

## 输入-输出空间
- **输入**：应用层交来的字节流 + 接收方反馈的ACK（含确认号和接收窗口）
- **输出**：发送方调整发送窗口和重传决策 + 接收方按序交付数据给应用层
- **映射关系**：映射关系 — 确认号驱动窗口滑动，窗口大小决定发送行为

## 正例（至少2个）
1. **累计确认**：客户端连续发送序号603~604和605~606的两个报文段，服务器收到后只需返回一个ACK=607，表示607之前所有字节已正确接收——有效减少ACK数量。
2. **快重传优化**：客户端连续发4个报文段（序号622~625），第二个丢失。服务器收到其余3个，每个都返回ACK=623（冗余ACK）。客户端收到3个冗余ACK后立即重传622，不等超时——大幅减少等待时间。

## 反例/边界（至少1个）
1. **与数据链路层滑动窗口的区别**：数据链路层的窗口以**帧**为单位，作用于相邻节点之间（点到点）；TCP的滑动窗口以**字节**为单位，作用于端到端（进程到进程）。二者机制相似但层次和粒度不同。

## 详细解释

### 核心四个字段
| 字段 | 缩写 | 含义 |
|------|------|------|
| 序号 | SEQ | 当前段中第一个字节在字节流中的位置 |
| 确认号 | ACK seq | 在此号之前的所有字节已正确接收（需ACK=1标志有效） |
| ACK标志位 | 大写ACK | 控制确认号是否有效（除握手一外均为1） |
| 窗口 | RWND | 接收方告知自己的剩余接收能力（字节单位） |

### 可靠传输三大机制

#### 1. 序号机制
- TCP是**面向字节流**的：不关心应用层报文边界，将所有数据视为连续的字节流
- 建立连接时确定**起始序号**（如599），每个字节分配唯一的序号
- 序号使接收方能够**排序重组**乱序到达的报文段
- 握手一/握手二即使不携带数据**也要消耗1个序号**

#### 2. 确认机制
**累计确认**：确认号N表示"N之前的所有字节都已正确接收"
- 即使收到多个报文段，只需返回最大连续字节的确认号

**捎带确认**：接收方可在返回ACK时**顺带发送自己的数据**
- 提高传输效率（数据和控制信息合并到一个报文段）

**推迟确认**（传统方式）：
- 收到报文段后最多等待**0.5秒**再返回ACK
- 优点：利用累计确认，一个ACK确认多个段
- 缺点：个别段丢失时可能导致多个段无效重传
- 特殊规则：连续收到2个MSS段时必须立即确认

**立即确认**（快重传的基础）：
- 每收到一个报文段（含失序）**立即**返回ACK
- 失序到达的段产生**冗余ACK**（重复报告缺失的序号）

#### 3. 重传机制
**超时重传**：
- 每发出一个报文段，启动超时重传计时器
- 计时器到期未收到ACK → 重传该段并重置计时器
- 适用于：报文段丢失、ACK丢失等所有异常情况

**快重传**（优化机制）：
- 当发送方**连续收到3个冗余ACK**（确认号相同）时，**立即重传**该确认号对应的报文段
- 不等超时，大大减少重传等待时间
- 🚨 **易错点**：第一个ACK是正常的、合法的ACK，不算冗余。所谓"收到3个冗余ACK"实际是**连续收到1个合法ACK + 3个相同确认号的冗余ACK**（即共4个相同确认号的ACK），或表述为"收到3个确认号相同的冗余ACK（不包含第一个正常ACK）"
- 触发条件：立即确认 + 乱序到达 + 段丢失

**两种重传对比**：

| 特性 | 超时重传 | 快重传 |
|------|---------|-------|
| 触发条件 | 计时器超时 | 收到3个冗余ACK |
| 响应速度 | 慢（等待超时） | 快（立即重传） |
| 网络判断 | 严重拥塞 | 轻度拥塞 |
| 配合算法 | 慢开始 | 快恢复 |

### 流量控制（滑动窗口机制）

#### 核心概念
| 概念 | 说明 |
|------|------|
| **接收窗口（RWND）** | 接收方还剩多少缓冲空间，随数据交付而动态变化 |
| **发送窗口** | 发送方实际可发送的数据量 = min(拥塞窗口, 接收窗口) |
| **发送缓冲区** | 存放已准备好但尚未发送/已发送未确认的数据 |
| **接收缓冲区** | 存放收到的数据，按序交付给应用层 |

#### 工作流程
1. 接收方在ACK中携带自己的**接收窗口大小**
2. 发送方根据接收窗口调整发送窗口，确保**发送窗口 ≤ 接收窗口**
3. 已确认收到的数据移出发送缓冲区，空出位置填充新数据
4. 接收方数据交付应用层后，接收缓冲区变空，接收窗口增大

#### 特别说明
- 并非只有缓冲区满才交付给应用层：只要数据有序，可提前交付
- 乱序数据不能提前交付（必须保证按序交付）
- 接收窗口不能大于接收缓冲区的大小

### 快重传易错点总结
- 触发条件：**1个正常ACK + 3个冗余ACK**（共4个相同确认号的ACK被收到）
- 触发时间点：收到**第4个**相同确认号的ACK（即第3个冗余ACK）时
- 若考题描述为"收到3个确认号相同的反向ACK"→ 冗余ACK，已排除第一个正常ACK

## 细节备注

### 子特性
| 特性 | 说明 |
|------|------|
| 面向字节流 | TCP不关心应用层报文边界，视为连续字节流 |
| 累计确认 | 确认号N表示N之前所有字节已收，一次确认多个段 |
| 捎带确认 | ACK可顺带发送数据，提高效率 |
| 超时重传 | 最基本的重传机制，适用于所有异常情况 |
| 快重传 | 3个冗余ACK立即重传，无需等待超时 |
| 延迟确认 | 最多等0.5秒，利用累计确认减少ACK数量 |

### 易错提醒
- 快重传触发 ≠ 立即降低拥塞窗口到1（那是超时重传的处理）
- 快重传的"3个冗余ACK"不包含第一个正常ACK
- 发送窗口 = min(拥塞窗口, 接收窗口)，受二者共同约束
