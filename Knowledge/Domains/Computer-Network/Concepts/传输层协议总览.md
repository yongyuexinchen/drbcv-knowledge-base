# 传输层协议总览

## 类型判定
混合型 — 汇总传输层的两大协议（TCP 和 UDP）及其核心机制，既是概念目录也是关系网。

## 类比
**一句话比喻：** 传输层就像物流公司的「送货上门签收」服务——TCP 是**顺丰特快**（当面签收、验货、有问题当场换），UDP 是**普通平邮**（扔进邮箱、爱到不到、丢了就算了）。

| 维度 | 生活映射 |
|------|---------|
| 端口号 | 同一栋写字楼（IP）里的不同房间号（端口）——找到具体哪个公司（进程） |
| TCP 三次握手 | 打电话："喂？听得见吗？""听得见，你呢？""我也听得见，开始说正事" |
| TCP 四次挥手 | "我说完了""好的我知道了""我也说完了""好的拜拜"（双方各说一次"结束"+各确认一次） |
| TCP 拥塞控制 | 高速路收费站——车少时多放行，车多了限流（慢开始），堵死了关闸重来（快恢复） |

## 是什么
传输层位于应用层和网络层之间，提供**端到端（进程到进程）的通信服务**。核心机制是**端口号**（16 位，标识主机上的进程）和**复用/分用**（多个应用层进程共用传输层协议）。传输层提供两种截然不同的协议：**TCP**（面向连接、可靠、复杂）和 **UDP**（无连接、不可靠、简洁）。

---

## 一、TCP vs UDP 对比（考研必考）

| 维度 | TCP | UDP |
|------|-----|-----|
| **连接方式** | **面向连接**（通信前需建立连接） | **无连接**（直接发送） |
| **可靠性** | 可靠（确认+重传+序号） | 不可靠（尽最大努力交付） |
| **首部大小** | 最小 20 字节，最大 60 字节 | **固定 8 字节** |
| **传输单位** | 报文段（segment） | UDP 数据报 |
| **通信方式** | 仅一对一（全双工） | 一对一、一对多、多对多（支持广播/多播） |
| **拥塞控制** | ✅ 有（慢开始、拥塞避免、快重传、快恢复） | ❌ 无 |
| **流量控制** | ✅ 有（滑动窗口） | ❌ 无 |
| **差错检测** | 有（检测出错→通知发送方**重传**） | 有（检测出错→直接**丢弃**，不通知） |
| **适用场景** | 文件传输、网页、邮件（要求可靠） | 直播、视频通话、DNS 查询（要求实时） |

## 二、TCP 核心机制

### 2.1 TCP 报文段结构

| 关键字段 | 长度 | 说明 |
|---------|------|------|
| 源/目的端口 | 各 16 bit | 标识发送方和接收方进程 |
| **序号（seq）** | 32 bit | 本报文段数据第一个字节的编号 |
| **确认号（ack）** | 32 bit | 期望收到对方下一个报文段的序号 |
| 首部长度 | 4 bit | 以 4 字节为单位 |
| 标志位 | 6 bit | **SYN**（同步）、**ACK**（确认）、**FIN**（结束）、RST、PSH、URG |
| **窗口大小** | 16 bit | 接收方当前可用的缓冲区大小（用于流量控制） |
| 校验和 | 16 bit | 校验首部+数据 |
| 紧急指针 | 16 bit | URG=1 时有效 |

> 详细内容 → [[TCP报文段]]

### 2.2 连接管理：三次握手 + 四次挥手

| 阶段 | 过程 | 关键标志位 |
|------|------|-----------|
| **三次握手（建立连接）** | ① 客户→服务器：SYN=1, seq=x（请求同步）| SYN |
| | ② 服务器→客户：SYN=1, ACK=1, seq=y, ack=x+1（确认+同步）| SYN+ACK |
| | ③ 客户→服务器：ACK=1, seq=x+1, ack=y+1（确认）| ACK |
| **四次挥手（释放连接）** | ① 客户→服务器：FIN=1（我不发了）| FIN |
| | ② 服务器→客户：ACK=1（收到，但我可能还有数据要发）| ACK |
| | ③ 服务器→客户：FIN=1（我也发完了）| FIN |
| | ④ 客户→服务器：ACK=1（好的拜拜）→ 等待 2MSL 后关闭 | ACK |

> 详细内容 → [[TCP连接管理（三次握手与四次挥手）]]

### 2.3 可靠传输机制

| 机制 | 说明 |
|------|------|
| **序号** | 每个字节编号，用于确认和重传 |
| **确认（ACK）** | 累积确认："期望收到下一个字节的序号" |
| **超时重传** | 计时器超时未收到 ACK → 重传该报文段 |
| **快重传** | 收到 3 个冗余 ACK → 不等超时，立即重传 |

### 2.4 流量控制（滑动窗口）

接收方通过 **窗口大小字段** 告诉发送方"我还能接收多少字节"。发送方据此调整发送窗口，防止发送过快超出接收方处理能力。窗口为 0 时发送方停止发送，但会发探测报文检查窗口是否恢复。

### 2.5 拥塞控制（四大算法）

| 算法 | 触发条件 | 核心行为 |
|------|---------|---------|
| **慢开始** | 新建连接 / 超时后 | cwnd 从 1 开始**指数增长**（每 RTT ×2），直到达到 ssthresh 阈值 |
| **拥塞避免** | cwnd ≥ ssthresh | cwnd **线性增长**（每 RTT +1），缓慢探测可用带宽 |
| **快重传** | 收到 3 个冗余 ACK | 不等超时，**立即重传**丢失的报文段 |
| **快恢复** | 快重传后 | ssthresh = cwnd/2，cwnd = ssthresh，**直接进入拥塞避免**（而非慢开始） |

> 详细内容 → [[TCP可靠传输与流量控制]]、[[TCP拥塞控制]]

## 三、UDP 协议

| 特征 | 说明 |
|------|------|
| **首部** | 固定 8 字节（源端口+目的端口+长度+校验和） |
| **校验和** | 包含伪首部（IP 地址），可选（IPv4） |
| **应用场景** | DNS 查询（快）、流媒体/直播（实时）、RIP 路由更新（简单） |

## 正例（≥2个）

1. **TCP 可靠传输实战**：浏览器请求一个网页 → TCP 三次握手建立连接 → HTTP 请求报文被 TCP 封装成多个报文段（seq=1~1460, seq=1461~2920, ...）→ 接收方返回 ACK 确认 → 若有报文段丢失（如 seq=1461 未收到），接收方持续回复 ack=1461 → 发送方超时或收到 3 个冗余 ACK → 重传丢失段。
2. **UDP 用于 DNS 查询**：浏览器输入 https://www.bilibili.com → DNS 客户端发送一个 ≤512 字节的 UDP 查询报文到本地 DNS 服务器（端口 53）→ 服务器在 UDP 报文中返回 IP 地址。整个过程无连接、无握手——一个请求-响应对就搞定。

## 反例/边界（≥1个）

1. **UDP 校验和不是可选项（IPv6）**：在 IPv4 中 UDP 校验和可选（为 0 表示不校验），但在 IPv6 中**必须计算校验和**（包含伪首部中的 IPv6 地址）。所以不能说"UDP 校验和总是可选的"。
