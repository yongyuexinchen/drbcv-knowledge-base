# Event Stream（事件流）

## 类型判定
判别型 — 用户每一个动作形成的「事件河流」，是 AI 伴侣理解用户行为的原始信号源。

## 类比 ★
### 一句话比喻
Event Stream 像一个人的「生活监控录像」——你什么时候起床（登录事件）、吃了什么早餐（点餐事件）、跟谁说了什么话（对话事件）、晚上几点关灯（退出事件）。这卷录像带不断录制，AI 伴侣需要从中剪辑出「你到底是个什么样的人」。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| 事件流（连续事件序列） | 生活监控录像——24 小时不断录制，每个动作是一帧 |
| 事件（不可变记录） | 监控录像的每一帧——发生过了就不可修改 |
| 事件时间戳 | 录像的时间码——精确到毫秒的事件发生时刻 |

## 是什么
事件流（Event Stream）是指按时间顺序持续生成的不可变事件序列。在 AI 伴侣系统中，用户的每一个交互行为都是一个事件：发送消息、点击按钮、上传文件、语音通话开始/结束、表情反应……这些事件被记录为包含时间戳、事件类型、负载数据（payload）的结构化记录，形成一条持续流动的「事件河流」。系统通过消费和分析这条河流来构建用户画像、触发自动化流程、训练模型。

## 输入-输出空间
- **输入**: 用户交互行为（来自 App、Web、语音接口等前端触点）
- **输出**: 有序、不可变的事件序列，存储于 Kafka / Pulsar 等消息队列
- **事件结构**: `{event_id, user_id, event_type, timestamp, payload, session_id}`

## 正例（≥2 个）
1. **对话事件流**: 用户说「今天好累」→ 事件 `{type: message_sent, payload: "今天好累", emotion: sad}` → 流入 Kafka → 触发 Memory 更新 + 情绪分析
2. **用户行为事件流**: 用户点击「晚安模式」→ 事件 `{type: mode_switch, payload: goodnight}` → 触发一系列自动化（调暗屏幕、播放白噪音）

## 反例/边界（≥1 个）
1. **批量日志文件**: 传统的每天一次导出的日志文件——不是「流」，是「批」。虽然可以从日志回放事件，但失去了实时响应的能力
2. **边界 — 事件风暴**: 如果每个鼠标移动都发事件，流会爆炸——需要在前端做采样/聚合，只保留「有意义」的事件

## 详细解释
事件流在 AI 伴侣架构中的位置：
```
用户交互（前端）
    ↓ 产生事件
[Event Stream] → Kafka Topic
    ↓ 消费事件
├─ 实时处理（Flink / Spark Streaming）：情感分析、异常检测
├─ 用户画像更新（User Profiling）：累积行为特征
├─ 触发自动化（Agent）：晚安模式 → 自动调暗灯光
└─ 离线分析（Spark 批处理）：周报、趋势洞察
```
关键设计原则：
- **不可变性**: 事件一旦产生不可修改——溯源和重放的基础
- **分区键**: 按 `user_id` 分区确保同一用户的事件被顺序处理
- **Schema 进化**: 事件结构会随时间变化，需要向后兼容的 Schema 管理（如 Avro/Protobuf）

## 关系
### → 指向
- [[Kafka]] — Kafka 是 Event Stream 最常用的传输和持久化平台
- [[Data Pipeline]] — Event Stream 是 Data Pipeline 的实时输入源
- [[User Profiling]] — 事件流数据是构建用户画像的原始材料

### ← 被指向
- [[Apache Spark]] — Spark Streaming 消费 Event Stream 做实时聚合
- [[ETL]] — ETL 的 Extract 阶段从 Event Stream 抽取数据
