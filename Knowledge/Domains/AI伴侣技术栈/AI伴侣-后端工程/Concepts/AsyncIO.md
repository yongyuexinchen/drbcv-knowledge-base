# AsyncIO

## 类型判定
判别型 — Python 的异步编程基础设施，让一个服务员同时招呼 100 桌客人的「分身术」。

## 类比 ★
### 一句话比喻
AsyncIO 像餐厅里最厉害的服务员——不等厨师做好一道菜才去接下一桌，而是「去厨房下单 → 马上回来接另一桌 → 听到铃响去取菜 → 端过去」，一个人顶十个用。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| `await` — 等待 IO 时交出控制权 | 服务员下单后不等在厨房门口——立刻转身去服务别的桌 |
| Event Loop — 事件循环 | 服务员的大脑——时刻扫描「哪个菜好了？哪桌在叫？」 |
| 同步阻塞（反面） | 服务员站在厨房门口死等，菜不出来就不动——全餐厅瘫痪 |

## 是什么
AsyncIO 是 Python 从 3.4 开始引入的异步编程框架，核心是 **事件循环（Event Loop）** + **协程（Coroutine）**。当一个协程遇到 IO 操作（如网络请求、数据库查询、文件读写），它用 `await` 将控制权交还给事件循环，事件循环切换到另一个就绪的协程继续执行。这让单线程能同时处理成百上千个并发 IO 任务，而不是为每个任务开一个线程。

## 输入-输出空间
- **输入**: `async def` 定义的协程函数
- **输出**: 通过 `await` 挂起和恢复的执行流程
- **核心原语**: `asyncio.gather()`（并发执行多个协程）、`asyncio.create_task()`（创建后台任务）

## 正例（≥2 个）
1. **并发调用多个 LLM**: 同时调用 GPT-4、Claude、DeepSeek 三个模型取最优回答——AsyncIO 让三个请求同时发出，等待时间 = 最慢的那个
2. **高并发聊天接口**: 100 个用户同时发消息，每个消息要查记忆、调 LLM、写数据库——AsyncIO 让一个进程处理所有请求，不等任何一个慢 IO

## 反例/边界（≥1 个）
1. **CPU 密集型计算**: 大数据排序、图像处理等任务会阻塞事件循环——应该用 `run_in_executor` 丢给线程池或直接用多进程
2. **边界 — 阻塞代码混入**: 在 `async def` 里调用了 `time.sleep(5)`（同步阻塞）而不是 `await asyncio.sleep(5)`——整个事件循环被卡住 5 秒

## 详细解释
AsyncIO 的事件循环模型：
```
     ┌─────────────────────────────────┐
     │         Event Loop              │
     │                                 │
     │  Task A: await call_llm()  ───→ 等待中...
     │  Task B: await db_query()  ───→ 执行中！
     │  Task C: await redis.get() ───→ 等待中...
     │                                 │
     │  Loop: A等→切B → B等→切C → 循环 │
     └─────────────────────────────────┘
```

在 AI 伴侣中，AsyncIO 的价值在于：LLM API 调用的延迟通常 1-5 秒，这期间如果不切走，一个线程只能服务一个用户。AsyncIO 让一个线程在等 LLM 回复时去处理下一个用户的请求——这是 FastAPI 高并发的基础。
