# Vector Database（向量数据库）

## 类型判定
判别型 — 专门存储和检索高维向量的数据库，语义搜索的「搜索引擎」。

## 类比 ★
### 一句话比喻
向量数据库像图书馆的「语义地图导航系统」——传统图书馆只能按书名首字母找书，向量数据库你说「我想找关于旅行的书」，它带你走到书架前，把《lonely planet》《背包十年》《国家地理》全摆在面前，哪怕书名里没「旅行」二字。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| 向量检索（ANN 近似最近邻） | 图书馆的语义导航——不翻目录，靠内容相似度直接找到书 |
| 普通数据库（SQL） | 老式图书馆目录柜——只能按书名/作者精确匹配，不懂「意思相近」 |
| HNSW 索引（高维图导航） | 图书馆内部秘密通道——不是一层层扫书架，而是跳跃式直达目标区 |

## 是什么
向量数据库是专门为高维向量数据设计的数据库系统，核心能力是**近似最近邻搜索（ANN）**——给定一个查询向量，在百万甚至亿级向量中快速找到最相似的 K 个。它不同于传统数据库的精确匹配，而是通过向量距离度量「语义相似度」。主流选择包括 Qdrant、Milvus、Chroma（轻量）、Weaviate、pgvector（PostgreSQL 扩展）。

## 输入-输出空间
- **输入（写入）**: 向量 + 元数据（Payload），如 `{vector: [0.2, ...], payload: {text: "用户说喜欢日料", user_id: 123}}`
- **输入（查询）**: 查询向量 + top-k + 可选过滤条件
- **输出**: top-k 个最相似向量 + 对应元数据 + 距离分数
- **索引算法**: HNSW（图索引，快但占内存）、IVF（倒排索引，省内存但略慢）

## 正例（≥2 个）
1. **AI 伴侣记忆检索**: 100 万条聊天记录全部向量化存入 Qdrant → 用户说「上次那家好吃的日料店叫什么」→ 检索返回最相关的 5 条记忆 → LLM：「是银座的『鮨一』对吧？」
2. **知识库问答**: 公司内部 5000 篇文档 → Embedding → Milvus → 员工提问 → 检索 top-3 片段 → LLM 基于原文回答

## 反例/边界（≥1 个）
1. **传统 SQL 搜索**: `SELECT * FROM docs WHERE content LIKE '%旅行%'` — 只能精确匹配，搜不到「出游」「远足」相关内容——这不是向量数据库的领域
2. **边界 — 精度 vs 速度权衡**: ANN 返回的是「近似」最近邻，不是绝对最近——对语义搜索足够，但不适合需要精确 Top-K 的场景

## 详细解释
向量数据库的核心索引算法 HNSW（Hierarchical Navigable Small World）：
```
Layer 2:  ○────○        ← 顶层稀疏图，跨大步跳跃
           │
Layer 1:  ○──○──○──○    ← 中层，中等步长
           │
Layer 0:  ○○─○○─○○─○○   ← 底层密集图，精细搜索
```
搜索从顶层的稀疏图开始，大步跳到目标区域，逐层往下细化，最终在底层找到最相似的向量。

在 RAG 管道中：
```
查询 Embedding → 向量数据库.search(top_k=5) → 5个最相似片段 → 注入 Prompt → LLM 回答
```

主流选择对比：
| 数据库 | 特点 | 适合场景 |
|-------|------|---------|
| Chroma | 轻量、Python 原生 | 开发原型、小规模 |
| Qdrant | Rust 编写、高性能 | 生产环境 |
| Milvus | 分布式、十亿级 | 大规模企业 |
| pgvector | PostgreSQL 扩展 | 已有 PG，想加向量 |
