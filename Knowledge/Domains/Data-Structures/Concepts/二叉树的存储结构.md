# 二叉树的存储结构（Storage of Binary Tree）

## 类型判定
判别型 — 区分二叉树的两种物理存储方式：顺序存储和链式存储，各自适用场景完全不同。

## 是什么
二叉树有两种物理存储结构：
- **顺序存储**：用数组按层序依次存放结点，借助下标运算反映父子关系
- **链式存储**：每个结点包含数据域 + 左孩子指针 + 右孩子指针（二叉链表），或再加父指针（三叉链表）

## 输入-输出空间
- **输入**：二叉树的逻辑结构
- **输出**：对应的物理存储表示
- **核心问题**：如何在存储结构中体现父子关系？

## 正例（≥2 个）
1. **完全二叉树的顺序存储**：编号为 i 的结点，左孩子在 2i，右孩子在 2i+1，父在 ⌊i/2⌋——数组下标完美反映逻辑关系
2. **普通二叉树的链式存储（二叉链表）**：直观、灵活，每个结点两个指针，n 个结点共有 2n 个指针域，其中 n+1 个为空（可用来构建线索二叉树）

## 反例/边界（≥1 个）
1. **普通二叉树用顺序存储**：必须按完全二叉树编号，缺失的结点也要留空位 → 大量空间浪费。最坏情况（所有结点只有右孩子）下，高度 h 的树需要 $2^h - 1$ 个存储单元
2. **二叉链表中找父结点**：给定结点 p，无法直接找到其父结点——必须从根开始遍历。如需频繁找父，应改用三叉链表

## 详细解释

### 顺序存储

```c
#define MaxSize 100
struct TreeNode {
    ElemType value;   // 数据
    bool isEmpty;     // 结点是否为空
};
TreeNode t[MaxSize];  // 从 t[1] 开始存储（下标与编号对齐）
```

核心规则：按**完全二叉树的层序编号**存放：
- 根结点在 t[1]
- i 的左孩子在 t[2i]，右孩子在 t[2i+1]
- i 的父结点在 t[⌊i/2⌋]

对于非完全二叉树，需要把缺失位置留空（isEmpty=true），造成空间浪费。

**结论**：顺序存储只适合**完全二叉树**，普通二叉树不推荐。

### 链式存储（二叉链表）

```c
typedef struct BiTNode {
    ElemType data;
    struct BiTNode *lchild, *rchild;
} BiTNode, *BiTree;
```

初始化一棵空树：
```c
BiTree root = NULL;                        // 空树
root = (BiTree)malloc(sizeof(BiTNode));
root->data = 1;
root->lchild = NULL;
root->rchild = NULL;
// 再插入左孩子
BiTNode *p = (BiTNode *)malloc(sizeof(BiTNode));
p->data = 2; p->lchild = p->rchild = NULL;
root->lchild = p;
```

**关键结论**：n 个结点的二叉链表共有 2n 个指针域，其中 **n+1 个为空**（n−1 个被用来连接结点，剩下 n+1 个悬空）。这些空指针域正好可以改造为**线索**（→ [[线索二叉树]]）。

### 三叉链表（方便找父结点）
在二叉链表基础上加一个 `parent` 指针。

## 类比

### 一句话比喻
**顺序存储就像电影院按座位号入场——1 号坐中间，2 号和 3 号坐他左右两边，4~7 号坐第三排……你只要知道自己的座位号，就能算出你孩子在哪儿（×2），你爸在哪儿（÷2）。但如果电影院没坐满，空座位也得留着——这就是空间浪费。链式存储就像微信联系人——每个人只知道自己的「左好友」和「右好友」是谁，想找他爸？翻遍通讯录问一圈才知道。**

### 生活映射
| 数据结构世界 | 现实世界 |
|---|---|
| 顺序存储（数组） | 电影院按号入座——座位号=编号 |
| i 的左孩子=2i | 你坐 5 号，你左孩子在 10 号 |
| 完全二叉树 | 满座电影场——没有空位 |
| 普通二叉树顺序存储 | 稀稀拉拉的场——空座也得留着牌子 |
| 二叉链表 | 微信群聊——每个人只知道「下一个聊友」是谁 |
| 空指针域（n+1 个） | 群里有 n 个人，但只加了 n−1 个好友，剩余「未加好友」的坑位 |
| 三叉链表 | 加了个「家人群」——不仅能找孩子，还能秒找到爹 |
