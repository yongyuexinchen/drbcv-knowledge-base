# SSE（Server-Sent Events）

## 类型判定
判别型 — 服务端到客户端的单向推送技术，ChatGPT 流式输出的「输送带」。

## 类比 ★
### 一句话比喻
SSE 像奶茶店的大屏幕叫号——你下单后不用一直跑去问「好了没」，屏幕（服务器）做好了就显示你的号，你看到就去取。但你不能通过屏幕告诉店员「多加点珍珠」——那是另一个通道的事。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| SSE 单向推送 | 奶茶店叫号屏——只能店推给顾客，顾客不能通过屏回复 |
| WebSocket 双向 | 面对面聊天——双方随时说随时听 |
| EventStream 流式 | 叫号屏一行一行往外蹦——不是一次性全显示，而是一个接一个 |

## 是什么
SSE 是 HTML5 标准的一部分，基于 HTTP 协议实现服务端向客户端的单向数据推送。客户端发起一个普通的 HTTP 请求，服务端保持连接不关闭，持续以 `text/event-stream` 格式推送数据。在 AI 伴侣中，SSE 是实现 LLM 流式输出的最简单方案——LLM 每生成一个 token，服务端就推送给前端。

## 输入-输出空间
- **输入**: 客户端 HTTP GET 请求（带 `Accept: text/event-stream`）
- **输出**: 服务端持续推送的 `data:` 行，格式为 `data: {"token": "你"}`
- **生命周期**: 客户端发起连接 → 服务端保持长连接 → 推送完数据后关闭或客户端断开

## 正例（≥2 个）
1. **ChatGPT 流式输出**: 用户问问题 → 服务端通过 SSE 逐 token 推送回答 → 前端逐字渲染
2. **AI 伴侣思考过程**: LLM 推理时实时推送「正在回忆你们的过往...」→ 「想到了3件事」→ 最后输出完整回复

## 反例/边界（≥1 个）
1. **需要客户端频繁发消息**: 对话场景用户每轮都要发消息——SSE 只能推不能收，用户消息仍需 HTTP POST，不如直接用 WebSocket 一条连接搞定收发
2. **边界 — 浏览器限制**: 同一域名下浏览器最多开 6 个 SSE 连接（HTTP/1.1），超过会被阻塞

## 详细解释
SSE 的消息格式非常简单：
```
data: {"token": "你", "index": 0}

data: {"token": "好", "index": 1}

data: [DONE]
```
每条消息以 `data:` 开头，双换行分隔。`[DONE]` 是约定俗成的结束信号。

在 AI 伴侣架构中的位置：
```
LLM 推理 → FastAPI StreamingResponse → SSE → 前端逐字渲染
```

与 WebSocket 的选择逻辑：如果只需要「服务端推送给客户端」（如流式输出、通知），SSE 更简单——不需要协议升级、防火墙友好、自动重连。如果需要「客户端也往服务端高频推送」（如语音实时交互），选 WebSocket。
