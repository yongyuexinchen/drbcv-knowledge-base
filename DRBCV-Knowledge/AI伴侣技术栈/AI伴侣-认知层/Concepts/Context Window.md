# Context Window

## 类型判定
判别型 — LLM 的「工作记忆容量」，决定一次能「看到」多少上下文。

## 类比 ★
### 一句话比喻
Context Window 像餐厅厨师眼前的备菜台——台面就这么大，一次只能摆这么多食材。菜太多（超长对话）就得把不用的端走，要用的再搬上来。台面越大，能同时处理的复杂菜品就越多。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| Context Window 大小（如 128K tokens） | 备菜台的面积——能同时摆多少食材 |
| 超出窗口的内容被截断 | 台面满了，最早摆上去的食材被撤走 |
| RAG 注入（精选内容进窗口） | 只挑 3 样关键食材上台面，不把整个冷库搬上来 |

## 是什么
Context Window 是 LLM 一次能处理的最大 token 数（输入+输出总和）。它决定了模型能「记住」多少对话历史、能参考多少文档。早期 GPT-3 只有 4K tokens（约 3000 中文字），现在的 Claude-3/DeepSeek 可达 128K 甚至 1M tokens。窗口越大，LLM 能处理的上下文越多——但成本也越高（按 token 计费）、推理越慢。

## 输入-输出空间
- **输入**: 所有放入窗口的内容（System Prompt + 历史消息 + RAG 结果 + 用户输入）
- **输出**: 生成的 token（与输入共享窗口）
- **约束**: 输入 token + 输出 max_tokens ≤ Context Window

## 正例（≥2 个）
1. **长对话保持连贯**: 128K 窗口可以放下一整天的聊天记录，AI 伴侣能记住几个小时前的对话细节
2. **代码库分析**: 把整个项目的代码放入窗口，LLM 一次理解全局架构——小窗口需要分段喂

## 反例/边界（≥1 个）
1. **超出窗口 → 截断遗忘**: 对话太长超出窗口，最早的对话被截断——AI 伴侣突然「忘记」你们半小时前说过什么
2. **边界 — 大海捞针问题**: 窗口很大（128K），但 LLM 对中间位置的内容注意力下降——信息放中间可能被忽略

## 详细解释
Context Window 的分配策略在 AI 伴侣中至关重要：
```
[System Prompt: 1K tokens]
[长期记忆摘要: 2K tokens]
[RAG 检索片段: 3K tokens]
[最近 20 轮对话: 8K tokens]
[用户当前输入: 500 tokens]
[max_tokens 输出: 4K tokens]
─────────────────────────────
总计: 18.5K / 128K — 还有余量
```

当对话越来越长，需要在「保留多少历史」和「留多少空间给输出」之间权衡。常见策略：
- **滑动窗口**: 只保留最近 N 轮
- **摘要压缩**: 旧对话自动压缩成摘要
- **分层记忆**: 重要记忆外挂存储，需要时检索注入
