# Streaming TTS（流式语音生成）

## 类型判定
判别型 — 边生成边播放的 TTS 模式，让 AI 伴侣的回应像真人一样「边说边想」，而不是「想完才说」。

## 类比 ★
### 一句话比喻
Streaming TTS 像真人聊天——你问「今天天气怎么样」，对方一边回答「今天...嗯...天气...」一边继续组织语言，不等全部想好了才一口气说出来。非流式 TTS 则像提前录好的语音信箱——必须全部录完才能播放。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| 流式逐 token 合成 | 实时口译——听到前半句就开始翻译，不等整段讲完 |
| 首包延迟（< 200ms） | 打电话的响应速度——「喂」一声马上听到回应 |
| 非流式整句合成 | 语音信箱——录完一整段才能点播放键听 |

## 是什么
流式 TTS 的核心是将「文本输入 → 音频输出」的管线改造为增量模式：每收到一个或一小段文本 token，就能立刻生成对应的音频帧并开始播放，而不需要等待整句文本到齐。这对 AI 伴侣至关重要——如果用户发了一段话，要等 LLM 生成完整回复 → TTS 合成完整音频，中间可能有 3-5 秒的「死寂」，体验极差。流式 TTS 把延迟降到 < 200ms 首包，让对话更像真人。

## 输入-输出空间
- **输入**: 增量文本 tokens（从 LLM 流式输出中逐 token 接收）
- **输出**: 增量音频帧（逐帧推送到播放器）
- **核心指标**: 首包延迟（TTFA，Time to First Audio）、播放流畅度（无停顿/跳帧）

## 正例（≥2 个）
1. **ChatGPT 语音模式**: GPT-4o 实时语音对话——用户的句子说完，GPT 的语音回应几乎同时开始
2. **CosyVoice 流式推理**: 阿里 CosyVoice 原生支持流式，首包延迟 < 150ms，适合 AI 伴侣语音交互

## 反例/边界（≥1 个）
1. **VITS 原生整句生成**: VITS 需要完整文本才能做对齐——必须等整句到齐→生成→播放，延迟 = LLM 时间 + TTS 时间（通常 2-5 秒），语音交互体验差
2. **边界 — 韵律连贯性**: 流式生成时，模型不知道后面的文本内容，可能在断句、语气上不如整句生成自然——需要在「延迟」和「韵律质量」之间权衡

## 详细解释
流式 TTS 的实现策略：
1. **分块合成**: 按标点或固定 token 数切分，每块独立合成 → 播放队列
2. **增量 Decoder**: 修改 Attention Mask，让 Decoder 支持增量推理
3. **Token-to-Speech**: 输入是 LLM 输出的 token，直接映射到音频 token（如 CosyVoice / GPT-4o 的做法）

在 AI 伴侣架构中：
```
LLM 逐 token 输出 → Streaming TTS → 音频帧 → WebSocket → 浏览器播放
                        ↑
              首帧 < 200ms，用户感知「即时回应」
```
