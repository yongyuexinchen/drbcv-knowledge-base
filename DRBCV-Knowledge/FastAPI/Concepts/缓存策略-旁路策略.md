# 缓存策略 — 旁路策略（Cache Aside）

## 类型判定
discriminant — 定义"先查缓存、再查库、写回缓存"的读写原则，区分于其他缓存策略（读写穿透、写回等），是一个设计决策而非单一操作步骤。

## 类比 ★
### 一句话比喻
旁路策略就像前台小黑板的"维护规则"：有人来问信息→先看黑板（查缓存），黑板上有就直接回答（命中），黑板没有才去档案室翻（查库），翻到后顺手抄黑板上（写回缓存）供下一个人用。如果档案室的档案更新了，要主动把黑板上的旧信息擦掉或更新（保证一致性）。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| 先查缓存，命中直接返回 | 先看黑板，有就直接说——最快路径 |
| 缓存未命中，查数据库 | 黑板上没有→去档案室翻——慢但能得到 |
| 查库后写入缓存 | 翻到档案后顺手抄黑板上——下次就快了 |
| 数据更新时删除/更新缓存 | 档案改了→把黑板上旧的擦掉——不能让人看旧信息 |
| 数据库与缓存一致性 | 档案室和黑板内容必须对得上——不能各说各的 |
| 不同数据不同过期时间 | 排班表每小时擦（常变），公司规章每周擦（稳定） |

## 是什么
旁路策略（Cache Aside）是应用层最常用的缓存策略，核心规则：
- **读**：先查缓存，命中直接返回；未命中 → 查数据库 → 把结果写入缓存 → 返回
- **写**：先更新数据库 → 删除/更新对应缓存（保证下次读拿到最新数据）

本质：**缓存在"旁边"辅助数据库，应用代码自己控制何时读缓存、何时写缓存**——Redis 不主动和数据库同步，完全由应用层管理。

## 正例（≥2 个）
1. **新闻分类缓存**（分类数据基本不变）：`get_cached_categories()` → 先 `get_json_cache("news:categories")` → 有则直接 return → 没有则查库 → `set_cache("news:categories", data, 7200)` → 返回。2 小时内所有请求命中缓存，数据库零压力。
2. **新闻列表缓存**（按分类+页码缓存）：`get_cached_news_list(category_id=1, page=2)` → 缓存 key 用 `news:list:1:2:10`（唯一标识）→ 有直接返回，没有查库写回。前端翻页时，每页独立缓存，互不冲突。
3. **数据更新后缓存失效**：编辑修改了某条新闻标题 → 先 `UPDATE news SET title=... WHERE id=...` → 再 `DELETE` 或更新对应缓存 key → 保证下次用户看到的是新标题。

## 反例/边界（≥1 个）
1. **只读缓存不更新**：数据改了，缓存还是旧的——用户看到过期信息。旁路策略要求**写操作必须同步处理缓存**（删或更新），否则产生脏数据。
2. **缓存所有请求**：把每次查询都缓存，导致 Redis 内存暴涨且命中率低——只缓存高频数据，冷数据走数据库即可。
3. **所有 key 同一过期时间**：假设所有 key 都是 3600 秒 → 同一时刻全部过期 → 瞬间海量请求打到数据库（缓存雪崩）。必须**错开过期时间**：分类 7200、列表 600、详情 1800、验证码 120。
4. **ORM 对象直接写缓存**：`set_cache("news", orm_obj)` → Redis 存的是 Python 对象内存地址的字符串表示，取出来无法还原。必须先用 `jsonable_encoder()` 转成 dict/list 再存。

## 详细解释
**旁路策略 vs 其他缓存策略**：

| 策略 | 读流程 | 写流程 | 适用场景 |
|------|-------|-------|---------|
| **旁路策略（Cache Aside）** | 应用先查缓存→未命中查库→写缓存 | 应用更新库→删/更新缓存 | 读多写少（新闻/电商） |
| 读写穿透（Read/Write Through） | 缓存层代理查库 | 缓存层代理写库 | 缓存与 DB 强绑定 |
| 写回（Write Behind） | 同旁路 | 只写缓存，异步刷库 | 写密集、可容忍少量丢失 |

**缓存雪崩**：大量 key 在同一时刻过期 → 所有请求同时穿透到数据库 → 数据库瞬间过载。对策：**不同数据类型设不同过期时间**（分类 2h、列表 10min、详情 30min），避免同时过期。

**代码改造模式**（以新闻分类为例）：
```python
# 改造前：直接查库
async def get_categories(db):
    return await db.execute(select(Category))

# 改造后：旁路策略
async def get_categories(db):
    # ① 先查缓存
    cached = await get_cached_categories()
    if cached:
        return cached
    # ② 缓存没有 → 查库
    categories = await db.execute(select(Category))
    categories = categories.scalars().all()
    # ③ 写入缓存
    if categories:
        await set_cached_categories(
            jsonable_encoder(categories),  # ← ORM → dict 转换
            expire=7200
        )
    return categories
```

**ORM 转换的必要性**：Redis 不认识 SQLAlchemy 的 ORM 对象。用 `jsonable_encoder()` 把 ORM 对象转为 list[dict] 格式，再通过封装的 `set_cache()`（内部自动 `json.dumps`）存入 Redis。取出时用 `get_json_cache()` 自动 `json.loads` 还原。
