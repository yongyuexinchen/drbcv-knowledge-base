# 缓存新闻列表

## 类型判定
procedure — 对新闻列表接口按旁路策略做缓存改造，核心是：设计唯一缓存 Key + ORM↔JSON 双向转换 + 路由层切换到缓存版 CRUD。

## 类比 ★
### 一句话比喻
缓存新闻列表就像把当天报纸的目录抄到前台黑板上——按照"栏目（category_id）+ 第几版（page）+ 每版几条（page_size）"给每页目录一个唯一编号，用户要哪页就直接看黑板，不用每次都去印刷车间（数据库）现印。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| 缓存 Key：`news:list:1:2:10` | 标签："体育版·第2版·每版10条"——唯一编号 |
| `category_id` 分类 | 报纸栏目：体育版 / 财经版 |
| `page` 页码 | 第几版——翻到哪一页 |
| `page_size` 每页条数 | 一版登几条新闻 |
| `skip → page` 反推公式 | 知道跳过了 20 条、每版 10 条 → 反推在第 3 版 |
| ORM → dict → JSON 存缓存 | 把印刷好的报纸拍照存电子档——Redis 只收电子格式 |
| 读缓存 → 列表推导式 → ORM | 从电子档还原成可读的报纸——程序要的是 ORM 对象 |

## 是什么
对新闻列表接口（`GET /api/news/list`）应用旁路策略：在 CRUD 层改造 `get_news_list` 方法，从"直接查库返回"变为"先查缓存 → 未命中查库 → 写缓存 → 返回"。关键点是设计**唯一缓存 Key**（`news:list:{category_id}:{page}:{page_size}`），以及 ORM 与 JSON 之间的**双向格式转换**。

## 输入-输出空间（程序型必填）
- **输入**：`category_id: int`（分类 ID，可选）、`page: int`（页码）、`page_size: int`（每页条数）
- **输出**：新闻列表（ORM 对象列表），响应格式不变
- **前置条件**：已封装 `get_json_cache` / `set_cache`、已定义 `NewsItemBase` 类型

## 核心代码 + 步骤表
```python
# ===== cache/news_cache.py：封装读写方法 =====

# 缓存 Key 前缀
NEWS_LIST_PREFIX = "news:list"

# 写入新闻列表缓存
async def set_cache_news_list(
    category_id: Optional[int],
    page: int,
    size: int,
    news_list: list,
    expire: int = 600          # 列表变化快，10 分钟过期
):
    # 拼接唯一 Key：news:list:1:2:10（分类1、第2页、每页10条）
    cat_part = str(category_id) if category_id is not None else "all"
    k = f"{NEWS_LIST_PREFIX}:{cat_part}:{page}:{size}"
    return await set_cache(k, news_list, expire)

# 读取新闻列表缓存
async def get_cache_news_list(
    category_id: Optional[int],
    page: int,
    size: int
):
    cat_part = str(category_id) if category_id is not None else "all"
    k = f"{NEWS_LIST_PREFIX}:{cat_part}:{page}:{size}"
    return await get_json_cache(k)

# ===== CRUD/news_cache.py：改造 CRUD =====
async def get_news_list(
    db: AsyncSession,
    category_id: int,
    skip: int,
    limit: int
):
    # ① 反推页码（因为缓存 Key 需要 page，但接口参数是 skip）
    page = skip // limit + 1                     # skip=20, limit=10 → page=3

    # ② 先查缓存
    cached = await get_cache_news_list(category_id, page, limit)
    if cached:
        # ③ 缓存命中 → JSON 转 ORM → 直接返回
        return [News(**item) for item in cached]

    # ④ 缓存未命中 → 查库（原逻辑不变）
    stmt = select(News).where(News.category_id == category_id)\
                       .offset(skip).limit(limit)
    result = await db.execute(stmt)
    news_list = result.scalars().all()

    # ⑤ 写入缓存（ORM → Pydantic → dict → JSON）
    if news_list:
        # 5a: ORM → Pydantic（只提取需要的字段）
        news_data = [
            NewsItemBase.model_validate(item).model_dump(
                mode="json", by_alias=False    # ← 保持 Python 下划线风格
            )
            for item in news_list
        ]
        # 5b: 写入 Redis
        await set_cache_news_list(category_id, page, limit, news_data)

    return news_list
```

| 步骤 | 做什么 | 关键代码 |
|------|--------|---------|
| ① 反推页码 | skip/limit → page | `page = skip // limit + 1` |
| ② 查缓存 | 按唯一 Key 读 Redis | `get_cache_news_list(cat_id, page, limit)` |
| ③ 命中→还原 | JSON → ORM | `[News(**item) for item in cached]` |
| ④ 未命中→查库 | 原 SQL 查询 | `select(News).where(...).offset(skip).limit(limit)` |
| ⑤a ORM→Pydantic→dict | 提取需要的字段 | `NewsItemBase.model_validate(item).model_dump()` |
| ⑤b 写入 Redis | dict → JSON 存入 | `set_cache_news_list(cat_id, page, limit, news_data)` |

## 正例（≥2 个）
1. **首页第 1 页命中**：用户刷头条首页，category_id=1, page=1, page_size=10 → Key=`news:list:1:1:10` → 缓存有 → `get_json_cache` 返回 list[dict] → `[News(**item) for item in cached]` 还原 → 直接返回，不查库。
2. **翻到第 3 页**：skip=20, limit=10 → `page = 20//10 + 1 = 3` → Key=`news:list:1:3:10` → 缓存没有 → 查库 → `NewsItemBase.model_validate()` 逐条转 → `model_dump(mode="json", by_alias=False)` 转 dict → 写入 Redis → 返回。
3. **无分类 ID（全部新闻）**：`category_id=None` → `cat_part="all"` → Key=`news:list:all:1:10` → 确保不会和具体分类的缓存冲突。

## 反例/边界（≥1 个）
1. **Key 不唯一导致数据冲突**：所有新闻列表用同一个 Key `news:list` → 第 1 页和第 2 页的内容互相覆盖，用户翻页看到重复数据。必须包含 category_id + page + page_size 确保唯一。
2. **ORM 对象直接写缓存**：`set_cache(k, [<News obj>, <News obj>])` → Redis 存的是对象内存表示（如 `<News object at 0x7f...>`），取出来完全无法还原。必须先转 dict/JSON。
3. **`by_alias=True`（默认）**：`model_dump(by_alias=True)` → 字段名变成驼峰（`categoryId`），Redis 里的数据风格不统一。后端缓存应该保持 Python 风格（`category_id`），`by_alias=False`。
4. **路由层忘了改引用**：CRUD 改造完了，但 `routers/news.py` 还在 `from CRUD import news`（旧版），调的永远是没缓存的老方法 → 缓存功能形同虚设。

## 详细解释
**为什么缓存 Key 要这么复杂？**

新闻列表不是"一个列表"，而是 N 个列表的笛卡尔积：
- 5 个分类 × 10 页 × 1 种 page_size = 50 个不同的"列表"
- 每个都需要独立缓存，Key 必须区分它们

所以 Key 模板 = `news:list:{category_id}:{page}:{page_size}` 是**业务维度的唯一标识**。

**页码反推公式**：`page = skip // limit + 1`
- skip=0, limit=10 → page = 0+1 = 1（第 1 页）✓
- skip=20, limit=10 → page = 2+1 = 3（第 3 页）✓
- 用 `//` 整除而不是 `/` 浮点除，因为 Redis Key 里不能有小数

**ORM ↔ JSON 双向转换的必要性**：

```
存入：ORM → Pydantic.validate() → model_dump(mode="json") → json.dumps → Redis
取出：Redis → json.loads → [dict, dict] → [News(**item) for item] → ORM 列表
```

- **存入时**：用 `NewsItemBase`（Pydantic 类型）做中介，只提取需要的字段（不存冗余关系字段），保持缓存精简
- **取出时**：用 `News(**item)` 构造 ORM 对象，让下游代码（路由/响应序列化）无感知——它拿到的还是 ORM 对象，不知道中间经过了缓存

**路由改造**：CRUD 层新增 `news_cache.py`（带缓存版本），路由层把 `from CRUD import news` 改为 `from CRUD import news_cache`——通过 import 切换而非改原文件，保留原版做参考。
