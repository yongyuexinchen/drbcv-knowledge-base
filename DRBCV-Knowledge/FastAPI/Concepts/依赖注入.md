# 依赖注入（Dependency Injection）

## 类型判定
procedure — 三步标准流程实现代码复用：定义依赖项 → 导入 Depends → 注入到路由。

## 类比 ★
### 一句话比喻
依赖注入就像自助餐厅的"公用蘸料台"——每个客人（接口）自己决定要不要蘸料（注入依赖），而不是厨师给每道菜都浇上酱油（中间件对所有请求生效）。要辣椒的取辣椒，要不辣的绕过就行。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| 依赖项（dependency） | 公用蘸料台——封装了可复用的调料 |
| Depends() 注入 | 客人自己拿碟子去蘸——主动声明"我要用这个" |
| 中间件 | 厨师给所有菜都浇酱油——每个请求被动执行 |
| 路由处理函数参数 | 客人拿回来的碟子——注入后就能用结果 |

## 是什么
依赖注入是 FastAPI 提供的**按需代码复用机制**：把重复的逻辑封装成函数/类（依赖项），在需要的路由处理函数中通过 `Depends()` 声明注入。FastAPI 收到请求时会自动调用依赖项，把返回值注入到路由函数的参数中。

## 输入-输出空间（程序型必填）
- **输入**：依赖项函数可接收查询参数、请求体等，由 FastAPI 自动解析
- **输出**：依赖项的 return 值 → 注入到路由处理函数的对应参数
- **前置条件**：`from fastapi import Depends`

## 三步法
```
# 第一步：定义依赖项（封装复用逻辑）
async def common_params(skip: int = Query(0, ge=0), limit: int = Query(10, le=60)):
    return {"skip": skip, "limit": limit}

# 第二步：在路由参数中注入
@app.get("/news/")
async def news_list(commons: dict = Depends(common_params)):
    # 第三步：直接使用注入结果
    return commons
```

## 正例（≥2 个）
1. **分页参数复用**：新闻列表、用户列表、分类列表都需要 `skip/limit` 分页参数——用依赖注入定义一次，三个接口各自注入，互不影响。
2. **数据库会话注入**：每个需要查数据库的接口注入 `get_db` 依赖项，拿到数据库会话——不注入的接口不创建连接，节省资源。
3. **用户身份验证**：只有需要登录的接口注入 `get_current_user` 依赖项，公开接口不注入——精细控制权限。

## 反例/边界（≥1 个）
1. **所有接口都需要的逻辑 → 用中间件**：如果每个请求都要记录日志、设置 CORS 头——那就应该用中间件而非依赖注入，否则每个路由都要手动加一遍 `Depends()`，反而重复。
2. **依赖项里不要调用自己**：`Depends(func_name)` 传的是函数名，不是调用结果 `func_name()`。写了括号 FastAPI 反而不认识。

## 详细解释
依赖注入 vs 中间件的核心区别：
| | 中间件 | 依赖注入 |
|---|---|---|
| 生效范围 | 所有请求自动执行 | 只有声明了 Depends 的接口执行 |
| 控制权 | 框架做主 | 程序员做主（按需注入） |
| 典型场景 | 日志、CORS、全局异常 | 分页参数、数据库会话、用户鉴权 |
## 一句话
就是把重复使用的代码封装起来，需要调用时调用
