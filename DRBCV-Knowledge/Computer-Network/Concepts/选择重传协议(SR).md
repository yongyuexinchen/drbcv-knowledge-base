# 选择重传协议(SR)

## 类型判定
连接型 — 回答"SR协议如何运作"，涉及发送窗口和接收窗口均大于1的滑动规则、逐帧确认、NAK请求重传和选择性重传的完整机制。

## 是什么
选择重传协议（Selective Repeat，SR）是一种高效的可靠传输协议。**发送窗口和接收窗口均大于1（WT>1, WR>1）**，且要求 **WR ≤ WT**。与GBN的最大区别是：接收方可以**逐个确认**每个正确帧（不支持累积确认），可以**缓存不按序到达的正确帧**；发送方只重传真正丢失或出错的帧（不后退重传）。此外引入了**NAK否认帧**（Negative Acknowledge），接收方检测到错误帧时主动请求重传，不必等待超时。这些改进使得SR在信道误码率较高时的效率明显优于GBN。

## 输入-输出空间
- **输入**：数据帧序列 + 接收方返回的逐帧ACK/NAK + 超时事件
- **输出**：连续发送帧 + 选择性重传帧
- **映射关系**：映射关系 — 发送方行为由"每个帧独立的确认状态"决定

## 正例（至少2个）
1. **帧丢失选择性重传**：发送方WT=4，发DATA4~DATA7，DATA5丢失。接收方收到DATA4（返回ACK4）、DATA6和DATA7（均接收并缓存，返回ACK6、ACK7），但DATA5因丢失未收到。DATA5计时器超时→发送方只重传DATA5。接收方收到DATA5后，将缓存中的DATA6、DATA7一起交付上层。避免了GBN中DATA6、DATA7也要重传的浪费。
2. **NAK主动请求重传**：发送方发DATA4~DATA7，DATA5接收出错。接收方丢弃DATA5并返回NAK5。发送方收到NAK5后立即重传DATA5（无需等超时），效率更高。

## 反例/边界（至少1个）
1. **累积确认不支持**：接收方连续收到DATA0、DATA1、DATA2，但必须分别返回ACK0、ACK1、ACK2（而非像GBN那样只返回ACK2）。因为接收方无法确认DATA0和DATA1之前是否有未收到的帧。

## 详细解释

### 协议四要素
| 要素 | SR的设定 |
|------|---------|
| **滑动窗口** | WT>1, WR>1（且 WR ≤ WT） |
| **确认机制** | **逐帧确认** — 每一个正确帧都返回单独的ACK；错误帧返回NAK |
| **重传机制** | 超时重传 + NAK主动请求重传（支持选择性重传） |
| **帧编号** | N比特，满足 WT+WR ≤ 2ᴺ |

### 窗口大小约束
SR有两个约束条件：
```
① WT + WR ≤ 2ᴺ
② WR ≤ WT
```
- 条件①：防止编号混淆（新旧帧编号不冲突）
- 条件②：充分利用窗口资源（WR过大时，超出的部分利用率低）
- 实际应用中通常取 **WT = WR**（对称窗口，效率最高）

### 与GBN的关键区别
| 比较维度 | GBN | SR |
|---------|-----|----|
| 接收窗口 | WR=1（顺序接收） | WR>1（可缓存乱序帧） |
| 确认方式 | 累积确认 | 逐帧确认 |
| 重传方式 | 后退N帧重传 | 选择性重传 |
| NAK | 不支持 | 支持（主动请求重传） |
| 缓存需求 | 接收方只需1帧缓存 | 接收方需WR帧缓存 |

### 三种异常处理
| 异常 | 处理方式 |
|------|---------|
| **数据帧丢失** | 超时后选择性重传该帧 |
| **数据帧出错** | 丢弃 + 返回NAK（请求重传）+ 超时兜底 |
| **确认帧丢失** | 发送方超时重传→接收方丢弃重复帧→重新返回ACK |

### 工作流程示意
```
发送方:    4→5→6→7    (WT=4)
                ↓ 5丢失
接收方:    4✓  6✓ 7✓  (WR=4，缓存6和7)
接收方返回: ACK4, NAK5, ACK6, ACK7
发送方重传: 5→
接收方:    5✓ → 交付4567给上层
```

## 生活类比
就像**有缓冲区的快递仓库流水线**——仓库（接收窗口WR>1）可以暂时存放多个包裹，不要求必须严格按序号摆上货架（缓存乱序帧）。如果发现包裹5破损，仓库立即通知你"包裹5破损，重新发一份"（NAK5），你只重新发包裹5（选择性重传），包裹6、7已经在仓库里等着了。相比GBN那种"包裹5破损→退回后面所有包裹"的方式，SR的效率高得多。
