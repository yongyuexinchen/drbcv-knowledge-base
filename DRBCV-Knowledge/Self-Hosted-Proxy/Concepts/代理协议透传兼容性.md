# 代理协议透传兼容性（通过 HTTP 反向代理）

## 类型判定
关系 — 不同代理协议（VLESS、VMess、Shadowsocks、Hysteria2）穿越 HTTP 反向代理（Cloudflare Tunnel）时的兼容性对比，是 3 天折腾的核心发现。

## 类比 ★
### 一句话比喻
VLESS = 密使接头——先对暗号、验身份、交换密码本，每个步骤都有严格顺序，中间人插一句"你好你找谁"（cloudflared HTTP 头）整个流程就断了。Shadowsocks = 封好的信件——信封（WebSocket）里是加密信纸（SS 流），邮递员（cloudflared）就算在信封上盖个章（X-Forwarded-For），信纸内容不受影响。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| VLESS 多轮握手 | 密使接头：先确认身份、再交换密码、再传递情报 |
| cloudflared HTTP 头干扰 | 邮局大妈非要拆开信封写备注 |
| Shadowsocks 纯加密流 | 封好的信：信封上盖章不影响信纸内容 |

## 是什么
在 Cloudflare Tunnel 的 L7 HTTP 代理环境中，cloudflared 会在 HTTP 连接上添加 `X-Forwarded-For` 等头，并可能缓存/重组成 WebSocket 数据帧。不同代理协议的握手复杂度和数据格式决定了它们能否无损穿透这层 HTTP 代理。

## 正例
1. **Shadowsocks + WebSocket ✅**：WebSocket 升级后直接发送加密 TCP 流，无握手阶段，cloudflared 看到的只是标准 WebSocket 二进制帧，不做干预。
2. **ttyd (纯 HTTP/WebSocket) ✅**：ttyd 本身就是 HTTP 协议，与 cloudflared 完全匹配。

## 反例/边界
1. **VLESS + WebSocket ❌**：VLESS 有多轮握手（认证、加密协商、流控），cloudflared 在 WebSocket 升级后缓存并重组数据帧，打断握手时序。即使关了 Xray sniffing，cloudflared 创建的 HTTP 连接依然会扰乱 VLESS 的协议检测。
2. **VMess + WebSocket ❌**：与 VLESS 相同原因——VMess 的 AEAD 认证和加密协商需要完整的二进制帧序列。
3. **Hysteria2 ❌**：Hysteria2 基于 QUIC/UDP，完全不兼容 Cloudflare 的 HTTP/L7 代理栈。
4. **XHTTP / HTTPUpgrade ❌**：虽然设计上更接近 HTTP，实际测试中依然被 cloudflared 干扰握手。

## 详细解释
全部 9 次尝试的协议兼容性矩阵：

| 协议 | 传输 | 入站 | 结果 | 根因 |
|------|------|------|:--:|------|
| Hysteria2 | QUIC | CDN | ❌ | UDP 不解 HTTP |
| VMess | WS | CDN | ❌ | CF CDN 丢弃二进制帧 |
| VLESS | WS | CDN | ❌ | 同上 + TLS 模式干扰 |
| VLESS | WS | Tunnel | ❌ | cloudflared HTTP 破坏握手 |
| VLESS | XHTTP | Tunnel | ❌ | 同上 |
| VLESS | HTTPUpgrade | Tunnel | ❌ | 同上 |
| **SS** | **WS** | **Tunnel** | **✅** | **无握手，纯加密流** |
| ttyd | HTTP | Tunnel | ✅ | 原生 HTTP 协议 |

**核心发现**：不是 Cloudflare 故意拦截代理协议，而是 VLESS/VMess 的复杂协议握手与 cloudflared 的 HTTP 代理行为（缓存、重组、添加头）在时序上冲突。Shadowsocks 恰好因为"无握手"而完美绕过。
