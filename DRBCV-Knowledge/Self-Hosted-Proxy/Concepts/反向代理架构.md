# 反向代理架构（Reverse Proxy Architecture）

## 类型判定
混合 — 既定义了反向代理的概念（判别），也描述了多层反向代理的典型部署模式（程序/架构）。

## 类比 ★
### 一句话比喻
反向代理 = 写字楼的前台。访客（用户）只看到前台的统一门面（域名），不知道楼里有多少家公司（服务）。前台根据访客的来意（hostname + path）把你引到对应楼层——A 公司（SS 代理在 10000 端口）、B 公司（网页终端在 7681 端口）。

### 生活映射
| 概念世界 | 现实世界 |
|---------|---------|
| Cloudflare Tunnel | 写字楼的前台接待 |
| 不同 hostname 路由 | 访客说出公司名，前台引导到对应楼层 |
| 多个服务共享一个入口 | 一栋楼里藏着多家公司 |

## 是什么
反向代理部署在服务端，接收外部请求并转发到内部的多个服务。外部用户只看到代理的统一入口（域名 + 端口），内部的端口、协议、机器完全隐藏。Cloudflare Tunnel 就是一种反向代理——cloudflared 接收来自 Cloudflare 的请求，按 hostname 路由到不同的本地端口。

## 正例
1. **最终架构**：`ssh.yongyuexinchen.xin` → ttyd:7681，`vps.yongyuexinchen.xin` → Xray SS:10000，两个服务共享同一个 Cloudflare Tunnel 入口。
2. **传统 Nginx 反向代理**：`api.example.com` → localhost:8000，`web.example.com` → localhost:3000。

## 反例/边界
1. **不是正向代理**：正向代理 = 客户端配代理服务器地址（如 `127.0.0.1:10809`），由代理代为访问外网。反向代理 = 用户访问代理的域名，代理代为访问内网服务。
2. **不做 SSL 终止的反向代理**（如 HAProxy TCP 模式）才是真正的 L4 反向代理。Cloudflare Tunnel 虽然看起来是"隧道"，本质仍是 L7 HTTP 反向代理。

## 详细解释
本次项目的反向代理架构：
```
用户请求
  │
  ├─ https://vps.yongyuexinchen.xin/ws
  │     │
  │     ├─ Cloudflare 边缘 (TLS 终止)
  │     ├─ Cloudflare Tunnel (QUIC)
  │     ├─ VPS cloudflared
  │     └─ localhost:10000 (Xray SS Inbound)
  │
  └─ https://ssh.yongyuexinchen.xin/
        │
        ├─ Cloudflare 边缘 (TLS 终止 + Access 认证)
        ├─ Cloudflare Tunnel (QUIC)
        ├─ VPS cloudflared
        └─ localhost:7681 (ttyd 网页终端)
```

关键设计决策：
- **为什么要反向代理？** 家里电脑的 ISP 封锁了 VPS IP，无法正向直连。反向代理让 VPS 主动建立到 Cloudflare 的连接，家里电脑只需访问 Cloudflare（不被封锁的域名）。
- **为什么用 hostname 路由？** cloudflared 不支持端口路由（Tunnel 只有一个入口），只能用 hostname（`vps.` vs `ssh.`）区分不同服务。
- **为什么 Shadowsocks 放在最内层？** 因为 cloudflared 的 HTTP 代理会干扰 VLESS 握手，SS 无握手直接从外层 WebSocket 帧进入加密流。
